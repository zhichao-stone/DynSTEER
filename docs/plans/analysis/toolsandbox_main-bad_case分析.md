## 4. DynSTEER 评估薄弱点归纳

1. **没有同口径 correctness**：replay 只给 coverage/quality，没有对截断 final state 重跑 native scorer，导致“更懂任务”和“误报”无法区分。
2. **结构完成与质量失败并存**：full 与 fail stage/policy stop 可同时出现，最终标签难以解释；使用单一 overall score 会掩盖冲突。
3. **stop policy 的误停/迟停都存在**：低进度 stop 可能切掉关键恢复后缀；高进度 stop 则节省有限，且 Judge 时间可能让全流程更慢。
4. **质量惩罚影响模型区分度**：DS 增强伴随整体降分，尚未证明模型差异更接近真实能力，可能部分来自 Judge 偏好或模板。
5. **成本边界不完整**：缺少 Agent token、adaptation 调用成本与全流程 token，无法回答 token overhead share；复用 DEFAULT 轨迹也不能冒充真实在线效率。
6. **方法内 repeat 排名证据缺失**：`repeat_rank_consistency` 未生成，当前无法按约束判断排名稳定性。

## 5. 优先修复建议

- P1：为 replay 终态增加 ToolSandbox native scorer，对每条记录同时输出 native score、coverage、quality、stop 四层标签。
- P1：把 full+fail、full+stop、minefield+coverage 冲突设为显式一致性检查，不再静默汇总到 overall score。
- P1：建立 stop audit 集，尤其覆盖 high-native-score、progress≤30%、有关键后缀工具和 progress≥80% 四类样本。
- P2：补生成方法内 repeat_rank_consistency；增加按 case 的 Judge 分数频数与模板化检查。
- P2：记录 adaptation 实际调用/缓存与 Agent token，按全量和 stop 子集报告真实 pipeline time/token。
