# DynSTEER 算法问题核查报告与代码修订方案

> 生成日期：2026-07-14  
> 核查对象：`docs/plans/report/2026-07-13-DynSTEER针对Agent轨迹的动态阶段式评估完整算法梳理报告.md` 与当前 `dynsteer` 源码  
> 文档定位：先形成可讨论的核查结论与代码修订方案，暂不直接修改源码。  
> 约束遵循：本方案遵循 `docs/constraints/code.md`，先在 `docs/plans` 输出方案；不主动提交 git；后续代码落地需补充测试、API 文档与必要中文注释。

## 1. 总体结论

本次核查结论比较明确：当前实现已经具备“运行期按 milestone 触发阶段评估”的主流程，但算法层有多处把工程权宜当成策略本身的情况，尤其是 `required`、不确定性 `top2_score`、逐维粒度调度、expensive prompt 和 rubric 输入职责。

我建议将后续修订目标定为：

1. milestone 语义回归：milestone 全部都是必须满足的轨迹约束节点，DAG 并行只表示无依赖顺序，不表示可选。
2. 约束匹配语义收敛：明确 selector / source / operator 的来源和边界，移除未实现或重复含义过强的 operator。
3. 不确定性废弃当前 composite 公式和全局 `uncertainty/judge_confidence` 字段，改为 `StageEvaluationResult.dimension_confidence` 与 `StageEvaluationResult.dimension_uncertainty` 两个一等字段。
4. 维度体系显式文档化：当前七维不是直接来自某篇论文，应定义为 DynSTEER 本地轨迹质量维度，并用论文/benchmark 作为支撑来源，而不是伪称有单一外部出处。
5. 动态权重更新回到 Arora / Hedge 风格的指数乘法更新，但输入简化为每维 `1-score` 与每维 `uncertainty`，避免 `target/focus` 带来的解释负担。
6. 动态评估粒度必须回到“不同维度可用不同级别”的设计，不能继续用最高维度级别替代整体评估策略。
7. standard / expensive prompt 重构为维度感知评估；expensive 应提供逐维专项 prompt，并只输出本次评估维度的分数。

## 3. 分项核查与修订建议

### 3.1 milestone 设置

当前问题：

- `Milestone.required` 让 milestone 具有“可选/必选”语义，这与 milestone 本身的定义冲突。
- 并行分支应表示“无先后依赖”，不是“某些节点可跳过”。
- 当前 required 还渗入 coverage、pending、ready frontier no-progress、diagnostics 与报告字段，导致评估结果可能把未完成 optional milestone 视为非失败。

修订方案：

1. 删除或废弃 `Milestone.required` 的算法语义。
2. 所有 `graph.nodes` 都视为必须完成的 milestone。
3. 将 `required_ready_milestone_ids(...)` 改为 `ready_milestone_ids(...)`，监控全部 ready milestone。
4. 将 `pending_required_stage_results(...)` 改为 `pending_milestone_stage_results(...)`，自然结束后所有未完成 milestone 都生成 pending/fail/missing 诊断。
5. coverage 改为：`full = 所有 graph.nodes 均 matched`；`partial = 至少一个真实 milestone matched 但不是全部`；`none = 无真实 milestone 或无 matched`。
6. `adapter/toolsandbox/utils/convert.py` 中 `_matcher_nodes(..., required: bool)` 的参数名也应改掉。这里的 `required` 实际只是区分 milestone 和 minefield，不应继续污染 milestone 语义。
7. adapted case 读取时如果历史 JSON 中有 `required=false`，后续落地时建议直接忽略该字段或报错。考虑项目约束“不默认兼容旧接口”，我倾向于报错并要求重新生成 adapted case，避免隐性行为差异。

- `dynsteer/adapter/loader.py`
- `dynsteer/adapter/toolsandbox/utils/convert.py`
- `dynsteer/evaluate/matching/frontier.py`

### 3.2 约束匹配：Selector 与 Operator

当前事实：

- `selector` 来源于 adapter 生成的 adapted case JSON，读取时由 `parse_constraint(...)` 填入 `Constraint.selector`。
- 通用 selector 只支持：
  - `$`
  - `$.a.b.c`
  - 空值返回 `None`
- `source` 由 `ConstraintTarget` 决定：
  - `state_snapshot` 使用 boundary 最近 snapshot。
  - `metric` 使用 `trajectory.metrics`。
  - `tool_call` / `tool_result` / `step` 使用 boundary step。
- ToolSandbox adapter 生成的 snapshot constraint 基本使用 `operator="custom"`，真正评分由 `ToolSandboxConstraintScorer` 读取 metadata 和原 benchmark 约束函数完成。

补充说明：`selector`、`source`、`operator` 三者不要混在一起理解。`source` 决定“从哪里取证据”，`selector` 决定“在证据对象里取哪一小块值”，`operator` 决定“取出的值和期望/参考值之间如何比较”。用一个函数式表达可以写成：

```text
actual = select_value(resolve_source(constraint.target, boundary), constraint.selector)
reference = select_value(resolve_reference_source(...), constraint.selector)  # 仅 delta operator 需要
score = apply_operator(actual, expected_or_reference)
```

几个典型案例：

1. 状态字段精确匹配：  
   场景：要求用户邮箱已写入最终数据库状态。  
   配置示意：
   ```json
   {
     "target": "state_snapshot",
     "namespace": "default",
     "selector": "$.user.email",
     "operator": "equals",
     "expected": "alice@example.com"
   }
   ```
   执行过程：`source` 取 boundary 上最近的 `StateSnapshot`；`selector` 从 snapshot 的 `default` namespace 中取 `user.email`；`equals` 要求实际值与 expected 完全相等。该类约束适合检查结构化最终状态，但不适合模糊文本判断。

2. 工具调用名称或参数检查：  
   场景：阶段内必须调用 `send_email`，且调用参数中包含目标收件人。  
   配置示意：
   ```json
   {
     "target": "tool_call",
     "selector": "$.name",
     "operator": "equals",
     "expected": "send_email"
   }
   ```
   若要检查参数，可使用 `selector="$.arguments.to"`。此时 `source` 是 boundary step 对应的工具调用对象，不是全轨迹；因此它只能检查当前边界 step，不能表达“整个阶段曾经调用过某工具”。后者应由 adapter 在 milestone 边界选择或专用 scorer 中处理。

3. 工具结果状态集合判断：  
   场景：工具返回状态只要是 `ok` 或 `success` 即可通过。  
   配置示意：
   ```json
   {
     "target": "tool_result",
     "selector": "$.status",
     "operator": "one_of",
     "expected": ["ok", "success"]
   }
   ```
   `one_of` 是离散集合判断，适合枚举状态，不适合数值阈值。当前通用 operator 没有 `greater_than` / `less_than`，如果要做数值比较，应显式新增 operator 与测试，而不是用 `fuzzy_match` 变相实现。

4. 浅层包含与结构化包含的边界：  
   场景 A：消息文本中包含关键词。  
   ```json
   {"target": "step", "selector": "$.content", "operator": "contains", "expected": "booking confirmed"}
   ```
   场景 B：状态 JSON 至少包含一个目标子结构。  
   ```json
   {
     "target": "state_snapshot",
     "selector": "$.orders.order_123",
     "operator": "json_subsumes",
     "expected": {"status": "confirmed", "paid": true}
   }
   ```
   `contains` 只应表示浅层包含：字符串子串、列表元素、dict key。`json_subsumes` 才表示“actual 是结构化 JSON，且覆盖 expected 子结构”。二者不能混用，否则 LLM 或 adapter 作者会误以为 `contains` 可递归检查复杂 JSON。

5. delta operator：  
   场景：某个里程碑之后必须新增一条订单记录。  
   ```json
   {
     "target": "state_snapshot",
     "selector": "$.orders.order_123",
     "operator": "added",
     "reference_milestone_id": "m_before_create_order"
   }
   ```
   正确语义是：在参考 milestone 对应 snapshot 中 `$.orders.order_123` 不存在，而当前 boundary snapshot 中存在。当前通用 scorer 把 `reference_milestone_id` 直接当作 `snapshot_id` 查找，这个假设不稳；修订后应从 `ScoringContext.matched_snapshots` 里根据 milestone 命中结果找 reference snapshot。

6. ToolSandbox 专用 custom：  
   场景：原 benchmark 约束需要比较数据库表、SANDBOX namespace、tool_trace 序列等复杂对象。  
   配置示意：
   ```json
   {
     "target": "state_snapshot",
     "selector": "$",
     "operator": "custom",
     "evaluator_hint": "toolsandbox_snapshot_constraint",
     "metadata": {"constraint_index": 3}
   }
   ```
   `selector="$"` 表示把整个 snapshot 交给专用 scorer；`operator="custom"` 表示通用 scorer 不应尝试解释 expected，而应由 benchmark scorer 接管。这个设计可以保留 benchmark 原始判分能力，但也要求 metadata 必须可审计。

本节补充核查结论：

| 用户关心点 | 当前文档覆盖情况 | 还需落地到代码/API 的点 |
|---|---|---|
| Selector 作用 | 已明确为“从 source 取值后的路径选择器”，并通过状态字段、工具调用、工具结果、文本、delta、custom 六类案例说明。 | 在 `docs/apis/constraints.md` 写成正式规范，并给出只支持 `$` 与 `$.a.b.c` 的限制。 |
| Operator 作用 | 已明确为“actual 与 expected/reference 的比较方式”，并区分静态比较、delta 比较、benchmark custom。 | 删除或实现 `ast_match`，并为每个 operator 补边界测试。 |
| Source / selector / operator 边界 | 已说明 source 决定证据对象来源，selector 决定证据对象内部取值，operator 决定比较规则。 | prompt 中不要暴露过多 operator/namespace/raw actual，避免 LLM judge 被底层 scorer 字段牵引。 |
| 详细案例是否足够 | 目前案例覆盖了 `equals`、`one_of`、`contains`、`json_subsumes`、delta operator、`custom`。 | 如果后续保留 `fuzzy_match`，还应补一个“浅层文本相似，不用于结构化状态”的案例；如果删除 `ast_match`，无需补 AST 案例。 |

当前问题：

- `Operator.AST_MATCH` 在 enum 中存在，但通用 scorer 未实现，属于危险的“看似支持”。
- `equals` 与 `unchanged_since`、`contains` 与 `json_subsumes` 有相似边界，但语义不是完全重复：前者是当前值比较，后者是 reference/delta 或结构包含。
- `added/updated/removed/unchanged_since` 强依赖 reference source；通用 scorer 用 `reference_milestone_id` 查 `snapshot.snapshot_id == reference_milestone_id`，这对 milestone id 和 snapshot id 不是同一命名体系的场景不稳。ToolSandbox 的正确路径反而是专用 scorer 通过 `ScoringContext.matched_snapshots`。

修订方案：

1. 建立 operator 分层：
   - 通用静态比较：`equals`、`contains`、`one_of`、`json_subsumes`、`fuzzy_match`。
   - 通用 delta 比较：`added`、`removed`、`updated`、`unchanged_since`，必须有明确 reference source。
   - benchmark 专用：`custom`，必须由 `evaluator_hint` 与 metadata 指明 scorer。
2. 删除 `ast_match`，除非同步实现 AST scorer 和测试。
3. 为 `contains` 与 `json_subsumes` 写清边界：
   - `contains` 只做字符串、列表元素、dict key 的浅层包含。
   - `json_subsumes` 做结构化 JSON 子集匹配。
4. 修复 reference source 语义：通用 delta operator 不应把 `reference_milestone_id` 直接当 snapshot id。应统一走 `ScoringContext.matched_snapshots`，并在没有 matched snapshot 时返回 missing。
5. 在 `docs/apis/evaluate.md` 或新增 `docs/apis/constraints.md` 中给出 selector/operator 规范和例子。
6. 补充 tests：
   - selector 命中/未命中。
   - each operator 边界。
   - delta operator 的 reference snapshot。
   - custom operator 由 benchmark scorer 接管。

### 3.3 不确定性计算

当前问题：

- `top2_score` 主流程固定为 0，`u_margin` 实际退化成 `1 - top1/0.3` 的函数，不再表达“候选竞争不确定性”。
- `evidence_conflict` 固定 False。
- `u_threshold` 把阶段分数离 pass/warn/fail 阈值的距离当作“不确定性”，但这只表达“决策边界附近状态容易翻转”，并不表达 judge 对该结果是否可靠。
- `u_missing` 把必要字段缺失计入不确定性，但必要字段缺失在当前语义下应直接导致 hard constraint fail 或 missing/fail，而不是让失败结果再进入“不确定性加权”。
- 当前系数 `0.30/0.25/0.20/0.15/0.10` 未见数据校准，也没有论文或 benchmark 原文可支撑。
- `judge_uncertainty = 1 - judge_confidence` 是当前唯一仍然有意义的方向，但全局 `judge_confidence` 字段本身也应废弃；新结构中只保留逐维 `dimension_confidence`。

当前代码公式完整展开如下：

```text
top1 = interval.milestone_score.score or stage_score
top2 = 0.0
evidence_conflict = False
judge_uncertainty = 1 - judge_confidence

margin = max(top1 - top2, 0)
u_margin = 1 - clamp(margin / 0.3)
u_missing = clamp(required_fields_missing_ratio)
u_threshold = 1 - clamp(
  min(
    abs(stage_score - pass_threshold),
    abs(stage_score - warn_threshold),
    abs(stage_score - fail_threshold)
  ) / threshold_margin
)
u_conflict = 1 if evidence_conflict else 0
u_judge = clamp(judge_uncertainty)

uncertainty = clamp(
  0.30 * u_margin
  + 0.25 * u_missing
  + 0.20 * u_threshold
  + 0.15 * u_conflict
  + 0.10 * u_judge
)
```

因此当前实现里真正有变化的主要是 `top1`、`missing_ratio`、`stage_score`、`judge_confidence`。`top2` 和 `evidence_conflict` 是固定输入，不能当作真实不确定性信号。尤其是 `top2=0` 会让 `u_margin` 变成 `1 - top1/0.3` 的截断函数：当 `top1 >= 0.3` 时该项基本为 0，当 `top1 < 0.3` 时该项只是低 milestone score 惩罚，而不是候选竞争不确定性。

更严格的核查结论：

1. 当前 composite uncertainty 公式应废弃，而不是继续修修补补。
2. `u_margin` 应删除。除非系统真的产生同一阶段多个候选 milestone 或多个候选 verdict 的概率分布，否则 margin uncertainty 没有输入基础。
3. `u_threshold` 应删除。分数靠近阈值最多说明“调度策略可能需要复核”，不是 judge 结果本身不可靠。
4. `u_missing` 不应进入 uncertainty。必要字段缺失是确定性失败信号，应体现在 status、hard constraint、diagnosis 和 progress score 中。
5. `u_conflict` 在真实冲突检测实现前应删除；固定 False 的参数不应继续出现在函数签名和 metadata 中。
6. 后续不确定性必须改为逐维 `dimension_uncertainty_d`，来源于该维评估器对自己 verdict/score 的可靠性估计。由于每个维度的评估粒度级别是独立的，不确定性/置信度也必须与维度和评估级别绑定，不能再有全局 `uncertainty` 和全局 `judge_confidence`：

```text
dimension_uncertainty_d = 1 - dimension_confidence_d
```

这里的关键不再是设计复杂全局 uncertainty 公式，而是固定每个维度在 cheap / standard / expensive 级别下的 `dimension_confidence_d` 计算。

可参考的不确定度/置信度方法：

| 方法 | 论文/来源 | 可借鉴点 | DynSTEER 中的边界 |
|---|---|---|---|
| 校准定义 | Ferrer 等，*When Can We Trust LLM Graders? Calibrating Confidence for Automated Assessment*，2026，<https://arxiv.org/abs/2603.29559> | 置信度应估计 `P(M(x)=T(x) | x)`，并用 ECE、Brier、AUC、Coverage at Risk 等指标评估 | 该论文是教育自动评分，不是 agent 轨迹；可借鉴置信度评估框架，不能直接套数值 |
| token probability | 同上；G-Eval，<https://arxiv.org/abs/2303.16634> | 如果模型 API 返回 logprobs，可对 verdict token 或离散 score anchor 的概率质量求置信度 | standard 级默认采用；仅在 provider 不支持 logprobs 时退回 K=3 重复 judge |
| P(True) / 自评校准 | Kadavath 等，*Language Models (Mostly) Know What They Know*，2022，<https://arxiv.org/abs/2207.05221>；Lin 等，*Teaching Models to Express Their Uncertainty in Words*，2022，<https://arxiv.org/abs/2205.14334> | 说明模型自评概率在合适格式和校准后可以有用 | 不能把一次 prompt 中的裸 `judge_confidence` 当成最终置信度；至少要做后验校准 |
| self-consistency / agreement | Wang 等，*Self-Consistency Improves Chain of Thought Reasoning in Language Models*，2022，<https://arxiv.org/abs/2203.11171> | 多次采样后的 verdict/score 一致性可作为置信度信号 | agreement 不是 correctness，本项目只能把它作为“需要复核”的代理信号 |
| semantic entropy / SelfCheck | Kuhn 等，*Semantic Uncertainty*，2023，<https://arxiv.org/abs/2302.09664>；Manakul 等，*SelfCheckGPT*，2023，<https://arxiv.org/abs/2303.08896> | 对开放文本 evidence/diagnosis，可比较多次输出是否语义一致 | DynSTEER 的 judge 输出应尽量离散化，语义熵只用于 evidence 一致性，不作为主分数 |
| conformal / post-hoc calibration | Angelopoulos & Bates，*A Gentle Introduction to Conformal Prediction and Distribution-Free Uncertainty Quantification*，2021，<https://arxiv.org/abs/2107.07511>；Guo 等，*On Calibration of Modern Neural Networks*，2017，<https://arxiv.org/abs/1706.04599> | 有标注历史数据后，用校准集把基础置信度映射成更可靠概率或复核集合 | 需要人工标注或高可信 oracle，当前修订不纳入，避免引入第二套置信度算法 |

按 cheap / standard / expensive 固定设计 `dimension_confidence`：

1. cheap 级：结构化规则置信度，不使用 LLM 自报。
   - `progress`：如果来自支持的 deterministic operator、hard constraints 明确通过/失败、且 source/selector 均命中，则 `dimension_confidence[progress] = 1.0` 或接近 1.0。
   - 必要字段缺失或 hard constraint fail：这是确定性失败，不是不确定；`status=fail/missing`，`dimension_confidence[progress]` 仍可较高。
   - `tool_quality`：工具名、参数 schema、执行错误、空结果等结构化信号可给中高置信度；若只是启发式 warning，则置信度低一些。
   - `efficiency`：若有 task family 的历史 step/turn 分布或人工参考轨迹，可按相对开销给较高置信度；若只有固定 `step_count > 12`，只能作为低置信诊断，不应强判。
   - cheap 层直接输出 `dimension_confidence`，不要输出全局 `judge_confidence`。

2. standard 级：单次 LLM judge 的外部置信度估计。
   - 默认采用单次 judge 的 token probability：prompt 输出离散 `status` 与离散 score anchor，例如 `{0, 0.25, 0.5, 0.75, 1.0}`，程序读取所选 status / score anchor token 的 logprobs，计算 `dimension_confidence_d`。
   - 建议公式：

```text
p_status = probability(selected_status_token)
p_score_d = probability(selected_score_anchor_token_for_dimension_d)
dimension_confidence_d = sqrt(p_status * p_score_d)
dimension_uncertainty_d = 1 - dimension_confidence_d
```

   - 只有当当前 LLM provider 不支持 logprobs 时，才退回 `K=3` 低温重复 judge，并用 status / score anchor 分布的归一化熵计算 `dimension_uncertainty_d`。
   - 禁止：继续让 LLM 自己输出 `judge_confidence` 并直接采用。

3. expensive 级：多 pass / 多 prompt 的一致性置信度。
   - 固定对每个 expensive 维度独立跑 `K=3` 次，避免 expensive 成本过高。
   - 将分数离散到 score anchor，统计各 anchor 的分布。
   - 用归一化熵计算不确定性：

```text
p_status(s) = count(status = s) / K
U_status = H(p_status) / log(|StageStatus|)

p_score_d(a) = count(score_anchor_d = a) / K
U_score_d = H(p_score_d) / log(5)

dimension_uncertainty_d = max(U_status, U_score_d)
dimension_confidence_d = 1 - dimension_uncertainty_d
```

   - 如果需要检查 evidence 是否稳定，可额外计算 sampled evidence 的语义一致性，但它只作为 diagnosis，不进入主公式。

4. 当前修订不引入后验校准器。后验校准需要人工标签或高可信 oracle，会改变评估算法边界；如果未来单独做校准实验，应另立方案，不混入本轮核心流程。

修订方案：

1. 删除 `compute_uncertainty(...)` 当前 composite 公式，移除 `top2_score`、`missing_ratio`、`stage_score`、`evidence_conflict`、`thresholds` 等入参。
2. `StageEvaluationResult` 直接废弃全局字段：
   - 删除 `uncertainty: float`。
   - 删除 `judge_confidence: float`。
3. `StageEvaluationResult` 新增一等字段：

```python
dimension_confidence: dict[Dimension, float]
dimension_uncertainty: dict[Dimension, float]
```

4. `dimension_confidence` 和 `dimension_uncertainty` 是报告、面板、权重更新和 policy 调度的正式字段，不放入 metadata。
5. 不新增任何置信度方法字段或原始信号字段。各级别评估器的置信度计算方法是固定算法，不需要每条结果额外标注。
6. `CheapJudge._confidence(...)` 删除或改为私有逐维 helper，不再返回全局分数。
7. `LLMJudge` payload 不再要求 `judge_confidence`；standard / expensive prompt 输出 score anchor，置信度由程序根据固定规则计算。
8. 测试要求：
   - hard constraint 缺失时结果为 fail/missing，且不通过 `u_missing` 增加不确定性。
   - 固定 `top2_score=0` 和固定 `evidence_conflict=False` 不再出现在 metadata。
   - expensive 多 pass 分歧越大，`dimension_uncertainty_d` 越高。
   - cheap deterministic hard fail 的置信度高于启发式 efficiency warning。
   - 当某一维是 cheap、另一维是 expensive 时，两者的 `dimension_uncertainty` 来源和计算方法可以不同，且互不覆盖。

### 3.5 动态权重更新

当前问题：

- 当前公式是指数乘法更新：

```text
next_weight_d ∝ current_weight_d * exp(alpha * deficit_d + beta * uncertainty * focus_d)
```

- 这个形式可以说受到 multiplicative weights / Hedge 的启发，但不是标准 Hedge，因为这里不是按专家损失做 regret minimization，而是把低分维度和不确定维度增权。
- `target`、`focus`、`alpha=0.8`、`beta=0.4` 没有校准来源。
- 从测试案例看，如果多个维度一起被不确定性项同向增权，归一化后实际权重变化会被抵消，动态性偏弱。
- 更根本的问题是，当前公式把 `target/focus` 与全局 `uncertainty` 混在一起，解释成本过高。对于本项目而言，动态权重只需要满足两个单调条件：上一轮某维分数越低，下一轮该维权重越高；上一轮某维不确定度越高，下一轮该维权重越高。

参考来源与公式边界：

1. Arora, Hazan, Kale, *The Multiplicative Weights Update Method: a Meta-Algorithm and Applications*，2012，链接：<https://theoryofcomputing.org/articles/v008a006/v008a006.pdf>。  
   论文中的标准 MWU 设置是维护多个专家/动作的权重，按每轮损失或收益更新，并归一化成分布。常见损失形式可写为：
   ```text
   w_i^(t+1) = w_i^t * (1 - η * m_i^t)
   p_i^t = w_i^t / Σ_j w_j^t
   ```
   其中 `m_i^t` 是第 `t` 轮专家 `i` 的损失/惩罚信号，`η` 是学习率。Hedge / exponential weights 的等价写法常用：
   ```text
   w_i^(t+1) = w_i^t * exp(-η * loss_i^t)
   ```
   或对收益信号写成 `exp(η * gain_i^t)`。

2. DynSTEER 当前公式与标准 MWU 的差异：  
   标准 MWU 的目标是在线学习/专家组合，并可分析 regret bound；DynSTEER 是把“某维度低分”和“该维度评估不确定”当成下一阶段注意力分配信号。这里的 `dimension` 不是专家，`1-score` 与 `uncertainty` 也不是论文中的专家损失，因此只能写成 `multiplicative-weights-inspired dimension reweighting`。

3. 当前公式归一化后的真实作用：  
   设归一化前：
   ```text
   raw_d = w_d * exp(alpha * deficit_d + beta * u * focus_d)
   next_d = raw_d / Σ_j raw_j
   ```
   任意两个维度 `a/b` 的相对权重比为：
   ```text
   next_a / next_b
   = (w_a / w_b) * exp(
       alpha * (deficit_a - deficit_b)
       + beta * u * (focus_a - focus_b)
     )
   ```
   所以只有 `deficit` 或 `focus` 的相对差异会改变归一化后的权重。如果多个维度的 `focus` 都是 1.0，`beta * u * focus` 是公共增益，会在归一化时抵消。这就是“权重更新幅度过小、动态性微弱”的主要原因之一。

修订方案：

1. 文档命名改成 `multiplicative-weights-inspired dimension reweighting`，不要称为标准动态权重算法。
2. target 的来源改为维度 rubric 的“期望合格线”：
   - progress/state/tool/safety 默认 0.8 或 0.9。
   - efficiency/interaction/recovery 是否使用 0.7，需要通过 benchmark 类型校准。
3. focus 改为 task type 下的维度优先级，不应是全局固定直觉值；如果没有校准数据，首版可以不让 focus 进入权重公式，只用于解释 policy 升级原因。
4. 针对“动态性体现微弱”，建议将全局不确定性从公共增益改为 deficit 的放大器，减少归一化抵消：

```text
deficit_d = max(0, target_d - score_d)
mean_deficit = Σ_j current_weight_j * deficit_j
relative_deficit_d = max(0, deficit_d - mean_deficit)
priority_d = task_focus_d

gain_d = exp(alpha * (1 + uncertainty) * relative_deficit_d * priority_d)
raw_next_weight_d = current_weight_d * gain_d
next_weights = normalize(raw_next_weights)
```

   解释：
   - `relative_deficit_d` 只奖励“比当前加权平均缺口更差”的维度，避免所有维度同向增加后被归一化抵消。
   - `uncertainty` 不再直接给所有高 focus 维度加同样的公共项，而是放大真实低分维度的增权幅度。
   - 该版本只保留 `alpha` 一个主要强度参数；若后续实验证明收益不明显，应继续简化。

5. 增加 `weight_update_diagnostics`：
   - `raw_gain_by_dimension`
   - `pre_normalized_weight`
   - `normalized_delta`
   - `dominant_dimension`
6. 增加回归测试：给定一组低分维度，下一阶段对应权重变化必须超过可见阈值。例如最大相对低分维度的权重相对提升至少 15%，同时非低分维度不能无理由同步上升。
7. 默认参数建议先通过 20-50 个历史 run 日志校准，不建议直接拍脑袋固定。如果必须给首版默认值，可从 `alpha=1.2~1.6` 做网格搜索；`beta` 建议先移除或只在对照实验中保留。
8. 若权重变化对最终评估结果、policy 升级、expensive 调用次数均无明显影响，应放弃复杂动态权重，只保留 task type 初始权重和逐维 policy level。

参考来源说明：

- 指数乘法更新可参考 Multiplicative Weights / Hedge，但当前公式的 target/focus/deficit 是项目自定义控制策略，不能声称来自论文。

### 3.6 动态评估粒度级别

当前问题：

- `EvaluationPolicyState.dimension_levels` 存在，但 `effective_level()` 取 `base_level` 与所有维度 level 的最高者。
- 这会把“某一维需要 expensive”变成“整个阶段所有维度都 expensive”，破坏原本的逐维动态策略。
- 当前 standard/expensive judge 的 payload 校验也强制输出所有七维，因此代码结构不支持逐维输出。

修订方案：

1. 删除或停止使用 `effective_level()` 作为唯一调度依据。
2. 不需要专门新增持久化的评估计划对象。当前 `EvaluationPolicyState.dimension_levels` 已经记录了各维度评估级别，调度时只需要从该字段即时分组即可：

```text
dimensions_by_level(policy):
  cheap = [d for d in Dimension if policy.dimension_levels.get(d, policy.base_level) == cheap]
  standard = [d for d in Dimension if policy.dimension_levels.get(d, policy.base_level) == standard]
  expensive = [d for d in Dimension if policy.dimension_levels.get(d, policy.base_level) == expensive]
```

   这里的 `dimensions_by_level` 可以是 evaluator 内部局部变量或私有 helper，不应新建与 `EvaluationPolicyState` 重叠的一等模型，避免状态重复。

3. 每个阶段执行：
   - cheap：可作为全维度低成本 baseline，或仅评估 cheap 维度。
   - standard：只评估 `dimension_levels == standard` 的维度组。
   - expensive：只评估 `dimension_levels == expensive` 的维度，且建议逐维调用专项 prompt。
4. 分数合并：
   - 先得到 cheap/base 分数。
   - standard 覆盖其负责维度。
   - expensive 覆盖其负责维度。
   - 最终 `StageEvaluationResult.dimension_scores` 仍保持七维完整，便于报告和权重更新。
5. status 合并规则：
   - `progress` 或 hard constraint fail 可决定阶段不通过。
   - `safety` expensive fail 可覆盖阶段 status。
   - 其他维度低分不应自动把 milestone 变成 unmatched，但会进入 diagnosis、weights 和 policy。
6. `LLMJudge._dimension_scores(...)` 改为支持 partial dimensions，不再强制全维度 payload。校验时应以本次 prompt 的 rubric keys 或 expected output schema 为准。
7. `judge_input_metadata` 中可以记录每次 judge 的维度集合，字段名可用 `requested_dimensions` 供审计；但这个字段不需要放进 prompt 的 `context_json`，因为 prompt 里 rubrics 和 output schema 已经只包含目标维度。
8. tests 必须覆盖：
   - 单一维度 expensive 时不会调用整阶段全维 expensive。
   - partial payload 只含请求维度也能校验。
   - 合并后 `StageEvaluationResult.dimension_scores` 仍完整。

### 3.7 cheap 级评估

当前问题：

- CheapJudge 的非 progress 维度来自工具失败、空结果、参数警告、grounding warning、额外用户 turn、step_count 等启发式。
- 这些规则可作为低成本 triage，但当前没有来源或校准说明。

来源判断：

- 目前没有看到一篇现有论文直接提出 DynSTEER 当前这种 `CheapJudge` 规则集，也没有论文给出“工具失败扣 0.1、空结果扣 0.08、step_count 超过 12 每步扣 0.02”这类具体扣分表。
- cheap 级评估更准确的定位是 deterministic heuristic triage：用结构化日志中已有的、无需 LLM 的信号，快速估计阶段风险。
- 它背后的思想可以被多篇工作间接支撑：ToolSandbox/τ-bench 支撑“工具执行和状态变化可被结构化检查”，HELM 支撑“多指标评估不只看 accuracy”，ReAct 支撑“agent 行为轨迹中的 action/observation 很重要”。但这些来源都不等于 cheap 规则本身。
- 如果拆到单个维度看，progress、tool_quality、efficiency 等维度确实可以从已有 benchmark 中借鉴“规则性评估”的设计，而不是完全凭空手写。

各维度 cheap 信号与参考边界：

| 维度 | 当前 cheap 可用信号 | 外部来源能支撑什么 | 外部来源不能支撑什么 |
|---|---|---|---|
| `progress` | milestone score、hard constraint、missing ratio | milestone/goal-state 式评估思路 | 具体 progress 公式和阈值 |
| `state_consistency` | failed_count、空结果、状态缺失 | stateful benchmark 关注最终状态 | 当前扣分权重 |
| `tool_quality` | 工具失败、参数警告、空结果 | ReAct/ToolSandbox 说明工具调用质量重要 | 工具失败到维度分数的线性映射 |
| `efficiency` | extra_user_turns、step_count | HELM efficiency 思想、成本敏感评估 | `step_count > 12` 的阈值 |
| `safety` | failed_count、minefield、policy warning | HELM risk/safety 与 benchmark policy constraints | 当前 cheap safety 扣分公式 |
| `interaction_quality` | grounding warning、额外用户 turn | LLM-as-a-Judge/MT-Bench 的对话质量评估范式 | 仅靠结构化 warning 评交互质量的充分性 |
| `recovery` | 失败后是否继续、failed_count | Reflexion/ReAct 支撑错误反馈与恢复重要 | 当前恢复分数扣分表 |

因此，cheap 级评估不应被描述为“有现成论文对应的方法”。它是本项目低成本筛查层，必须通过本项目数据校准。

拆分维度后的可借鉴做法：

1. `progress`：用 benchmark 规则判定目标是否完成。
   - ToolSandbox 把任务轨迹中的关键状态变化表示为 milestone 和 minefield，并在轨迹中寻找可满足 milestone 的 snapshot/turn 区间。它支持“阶段目标达成度可以由结构化状态约束直接计算”的思路。
   - τ-bench 更强调 tool-agent-user interaction 的任务成功率，核心仍然是通过环境/数据库最终状态和任务规则判断成功，而不是让 LLM 自由打分。
   - API-Bank 将 API 调用是否正确落到实际数据库查询、修改和返回结果上，说明 progress 可以由可执行环境状态检查支撑。
   - 对 DynSTEER 的启发：`progress` cheap 分数应优先来自 milestone hard constraints、state snapshot、database diff、tool execution result。若这些证据缺失，应该直接 fail/missing，而不是把缺失混入 uncertainty。

2. `tool_quality`：用工具名、参数、调用顺序和执行结果做规则检查。
   - API-Bank 把工具使用拆成 planning、retrieving、calling 三类能力，calling 的正确性依赖 API 调用与数据库操作结果是否一致。
   - Gorilla / APIBench 使用 AST 子树匹配检查 API 调用是否符合参考调用，并把不存在的 API 调用视为 hallucination。
   - ToolSandbox 对 snapshot constraints、tool traces 和 exception 做结构化检查，能支撑“参数错误、工具失败、空结果未处理”这些 cheap 信号。
   - 对 DynSTEER 的启发：`tool_quality` cheap 层不应只扣“failed_tool_results 数量”，而应拆成更透明的规则项：工具选择是否存在、参数 schema 是否满足、调用是否发生在合理阶段、工具结果是否被 agent 后续使用、失败后是否重试或降级。

3. `efficiency`：用 turn/step/tool-call 开销作为辅助指标，但不能用固定阈值冒充通用标准。
   - ToolSandbox 明确把 turn count 作为额外指标，因为 milestone 得分不惩罚多余交互；这能支撑 DynSTEER 保留 efficiency 维度。
   - ALFWorld/ALFRED/SPL 一类 embodied agent / navigation 评估把“完成任务”和“路径/动作开销”分开衡量，说明成功率之外可以单独评价执行效率。
   - 对 DynSTEER 的启发：`step_count > 12` 这类固定阈值不应作为通用扣分依据。更合理的做法是使用 task family 的历史分布、参考轨迹或 adapter 给出的 expected budget：

```text
expected_steps = task_family_stats.p80_steps 或 adapter.expected_steps
overhead = max(0, observed_steps - expected_steps) / max(expected_steps, 1)
efficiency_score = clamp(1 - overhead)
```

   - 如果没有历史分布或 expected budget，cheap 层只输出 `efficiency_warning`，不应把它强折算成低置信的数值扣分。

4. `state_consistency`：用声明、工具结果和状态快照的一致性检查。
   - ToolSandbox 和 τ-bench 都强调 stateful environment，适合借鉴为“agent 声称已完成，但数据库/状态未变”的规则检查。
   - 对 DynSTEER 的启发：cheap 层可以检测 agent final message 与工具结果/状态快照之间的明显矛盾，但自然语言声明是否充分仍应交给 standard/expensive。

5. `safety`：用 minefield、policy constraint、危险工具调用和不可逆操作确认做硬规则。
   - HELM 的 risk/safety 是多指标评估思想来源，ToolSandbox/τ-bench 的 domain-specific rules 能支撑把 policy violation 作为结构化规则。
   - 对 DynSTEER 的启发：cheap safety 应优先作为 hard fail / minefield penalty，而不是普通线性扣分。

6. `interaction_quality` 与 `recovery`：cheap 只能做弱筛查。
   - MT-Bench / LLM-as-a-Judge 说明对话质量更适合 rubric judge。
   - ReAct/Reflexion 支撑“错误识别、反馈、重试、恢复”是 agent 轨迹的重要行为。
   - 对 DynSTEER 的启发：cheap 可以捕捉“失败后完全忽略”“重复空结果仍断言成功”等明显模式，但细粒度沟通质量和恢复质量应由 standard/expensive 判断。

建议替换到当前 `CheapJudge` 的规则级评估方法：

| DynSTEER 维度 | 来源论文 / benchmark | 论文中的相关评估做法 | 可用于 DynSTEER 的规则级方法 | 与当前代码的最小改动 |
|---|---|---|---|---|
| `progress` | ToolSandbox: <https://arxiv.org/abs/2408.04682>；τ-bench: <https://arxiv.org/abs/2406.12045>；API-Bank: <https://arxiv.org/abs/2304.08244> | ToolSandbox 用 milestone / minefield 和状态快照评估轨迹；τ-bench 用领域规则和最终数据库状态判定任务成功；API-Bank 通过实际 API/数据库执行结果评价 API calling。 | `progress_score = milestone_score.score`；hard constraint fail 或 source/selector 缺失直接给 fail/missing；不要把 `missing_ratio` 解释为 uncertainty。 | 保留当前 `interval.milestone_score.score` 主逻辑；删除 `missing_ratio` 参与 uncertainty，只把它写入 diagnosis / metadata。 |
| `state_consistency` | ToolSandbox；τ-bench | 两者都强调 agent 声明、工具执行和环境状态必须一致，最终状态是核心证据。 | 从 `failed_tool_results`、`empty_tool_results`、`grounding_warnings`、状态缺失诊断中扣分；如果 agent 声称完成但状态证据不存在，降低该维。 | 当前 `base - 0.10 * failed_count` 太粗；改为 `base - 0.10 * failed_count - 0.08 * empty_state_warning - 0.08 * grounding_warning_count`，仍复用 `build_stage_quality_diagnostics()`。 |
| `tool_quality` | API-Bank；Gorilla / APIBench: <https://arxiv.org/abs/2305.15334>；ToolSandbox | API-Bank 拆分 planning / retrieving / calling，并以 API 调用与数据库结果检验 calling；Gorilla 用 API call 匹配和 hallucination 检查；ToolSandbox 保留工具 trace / exception / snapshot 约束。 | 检查工具是否被调用、工具名是否合理、参数 schema / argument warning、调用是否失败、结果为空后是否被错误使用。 | 基本保留当前 `failed_tool_results`、`empty_tool_results`、`tool_argument_warnings` 扣分；把扣分项写入 metadata，并可新增 `missing_expected_tool_call` / `result_not_used` 两个诊断。 |
| `efficiency` | ToolSandbox；ALFWorld: <https://arxiv.org/abs/2010.03768>；ALFRED: <https://arxiv.org/abs/1912.01734>；SPL / Embodied Navigation: <https://arxiv.org/abs/1807.06757> | ToolSandbox 报告 turn count，因为任务成功不惩罚多余交互；ALFWorld/ALFRED/SPL 将成功和路径/动作效率分开评价。 | 以多余用户轮次、重复工具调用、超过 task family budget 的 step/tool-call 作为扣分；没有 budget 时只给 warning，不强行用固定阈值。 | 保留当前 `extra_user_turns_before_first_tool_call`；把 `step_count > 12` 改为 `step_count > expected_step_budget`，默认 budget 可暂时沿用 12，但必须写成项目 fallback，不称为论文阈值。 |
| `safety` | ToolSandbox minefield；τ-bench domain-specific rules；HELM: <https://arxiv.org/abs/2211.09110> | ToolSandbox 用 minefield 捕捉不应发生的轨迹/状态；τ-bench 有领域约束；HELM 把 risk / safety 作为独立维度。 | safety cheap 应优先读取 minefield、policy warning、危险工具调用、不可逆操作缺少确认等硬规则；普通工具失败不应直接等同 safety 问题。 | 当前 `base - 0.15 * failed_count` 应改为优先使用 `minefield_score/policy_warning_count`；若暂时没有 policy 诊断，保留 failed_count 作为弱信号但降低权重并标注 `proxy_signal`。 |
| `interaction_quality` | MT-Bench: <https://arxiv.org/abs/2306.05685>；ToolSandbox turn count | MT-Bench 说明对话质量适合 judge；ToolSandbox 的 turn count 可规则化衡量用户额外负担。 | cheap 只评估可规则化的交互负担：不必要澄清、多余用户轮次、无法由工具/状态支撑却对用户断言。细粒度礼貌性、清晰度交给 standard/expensive。 | 保留当前 `grounding_warnings`；新增或复用 `extra_user_turns_before_first_tool_call` 对 interaction 做轻微扣分，而不只影响 efficiency。 |
| `recovery` | ReAct: <https://arxiv.org/abs/2210.03629>；Reflexion: <https://arxiv.org/abs/2303.11366> | ReAct 强调 action / observation 循环；Reflexion 强调失败反馈、反思和后续改进。 | 检查失败工具调用、空结果、参数错误之后是否有后续修正动作：重试、更换工具、向用户说明限制、停止不可靠断言。 | 当前 `base - 0.20 * failed_count` 容易误伤已恢复场景；改为 `base - 0.20 * unrecovered_failure_count`。只需在 diagnostics 中根据失败 step 后是否出现 successful tool result / corrective message 增加计数。 |

按这张表落地后，cheap 级评估仍然保持低成本和规则化，不引入 LLM，也不需要大规模重写当前结构。主要变化是：

1. `CheapJudge._dimension_scores(...)` 不再把 `failed_count` 同时粗暴影响多个维度，而是按维度使用有来源的规则信号。
2. `build_stage_quality_diagnostics(...)` 需要补充少量诊断项，例如 `expected_step_budget`、`policy_warnings`、`unrecovered_failure_count`、`missing_expected_tool_call`。
3. 每个 cheap 规则项在 metadata 中记录 `source_paper` 或 `project_fallback`，方便后续论文中说明哪些规则来自已有 benchmark 思路，哪些是 DynSTEER 的工程 fallback。
4. 如果某维没有足够规则来源，例如细粒度 `interaction_quality`，cheap 只输出 warning 和较低 confidence，不应强行替代 LLM judge。

修订方案：

1. 把 cheap 明确定位为 deterministic triage，不是精确裁决器。
2. 按维度重构 cheap 规则，不再把所有 warning 都塞进一个基础分扣分公式：
   - `progress`：只用 milestone / hard constraint / state diff。
   - `tool_quality`：工具选择、参数 schema、执行结果、结果使用。
   - `efficiency`：优先用 task family budget；无 budget 时只给 warning。
   - `safety`：minefield / policy hard rule。
   - `interaction_quality`、`recovery`：只做明显模式检测，不能替代 LLM judge。
3. 让 cheap 输出的 metadata 更透明：
   - 每个维度分数由哪些诊断项扣分。
   - 扣分权重是多少。
   - 每个规则项对应的参考来源或项目校准来源。
   - 每个维度的 `dimension_confidence`。
4. cheap 只用于：
   - 初筛。
   - 缺 LLM 时的降级报告。
   - 为 standard/expensive 提供 baseline。
5. 不再让 cheap 的启发式结果替代需要专项 LLM 判断的维度。
6. 删除或重写现有 `CheapJudge._confidence(...)`：全局 confidence 应被逐维 confidence 取代，且 hard fail / missing 不应被解释成“不确定”。

### 3.8 standard / expensive prompt

当前问题：

- `standard.zh.md` 和 `expensive_focus.zh.md` 差距较小。
- expensive focus 仍要求所有维度打分，不是真正专项评估。
- `context_json.rubric_dimension_focus` 总是全部维度。
- `rubric_dimensions` 没有详细评分规则。
- `structured_milestone_evidence` 太复杂，可能诱导 LLM 只看 scorer 结果，不认真审计轨迹 steps。

修订方案：

1. 目录结构调整：

```text
dynsteer/prompt/templates/judge/
  standard.zh.md
  standard.en.md
  expensive/
    progress.zh.md
    state_consistency.zh.md
    tool_quality.zh.md
    efficiency.zh.md
    safety.zh.md
    interaction_quality.zh.md
    recovery.zh.md
    adjudication.zh.md
    progress.en.md
    ...
```

2. standard prompt：
   - 支持一组目标维度。
   - 只要求输出目标维度。
   - 仍可使用通用模板，但 rubric 必须来自 context JSON。
3. expensive prompt：
   - 每个维度单独模板。
   - 每个模板有不同审查步骤，例如：
     - progress：拆解 stage_goal，逐条映射 step evidence。
     - state_consistency：核对工具结果、状态证据、agent 声明是否冲突。
     - tool_quality：检查工具选择、参数、调用时机、结果处理。
     - efficiency：检查重复调用、停滞、额外用户负担、无效 token/step。
     - safety：检查权限、不可逆操作、policy/hard constraint、敏感动作确认。
     - interaction_quality：只审计用户可见沟通，不用数据库状态复述作为硬要求。
     - recovery：检查失败识别、错误解释、重试、降级和停止。
4. context JSON 改造：

```json
{
  "stage_goal": "...",
  "rubrics": {
    "tool_quality": {
      "definition": "...",
      "score_anchors": {
        "1.0": "...",
        "0.75": "...",
        "0.5": "...",
        "0.25": "...",
        "0.0": "..."
      },
      "evaluation_steps": ["...", "..."]
    }
  },
  "constraint_checks": [
    {
      "constraint_id": "...",
      "constraint_goal": "...",
      "satisfied": true,
      "score": 1.0,
      "missing": false,
      "short_evidence": ["..."]
    }
  ],
  "steps": [],
  "required_output": {
    "dimension_scores": "只包含 rubrics 中出现的维度，例如 tool_quality",
    "status": "...",
    "evidence": "...",
    "diagnosis": "..."
  }
}
```

这里不需要专门提供 `requested_dimensions` 字段。只要 `rubrics` 只包含本次目标维度，且 `required_output.dimension_scores` 明确只输出这些维度，prompt 已经具备足够约束。`requested_dimensions` 可以保留在 `judge_input_metadata` 里供审计和调试，但不要放进面向 LLM 的 `context_json`，避免重复字段带来不一致风险。

5. `structured_milestone_evidence` 改为 `constraint_checks`：
   - 不直接暴露 operator/namespace/raw actual，除非 metadata 中开启 debug。
   - 每条 constraint 提供自然语言 `constraint_goal`。
   - prompt 明确说明：`steps` 是主要行为证据，`constraint_checks` 是 scorer 辅助证据，不能替代对阶段轨迹的审计。
6. constraint goal 来源：
   - 首选从 `Constraint.stage_goal_semantics` 确定性生成。
   - 若 semantics 不足，stage goal LLM 生成时同时生成 constraint-level objective。
   - 长期建议把 `TaskCase.stage_goals` 从 `dict[str, str]` 升级为结构化对象：

```python
@dataclass
class StageGoal:
    stage_id: str
    objective: str
    constraint_goals: dict[str, str]
```

## 4. 建议实施顺序

### Phase 1：语义清理与测试基线

目标：先把 milestone 必备语义和无效字段清干净。

任务：

1. 删除 `Milestone.required` 语义。
2. 重命名 required 相关函数、字段、测试。
3. coverage/pending/frontier watch 改为全部 milestone。
4. 删除 `Operator.AST_MATCH` 或补实现；建议先删除。
5. 补充 milestone DAG 并行分支测试：两个并行 milestone 都必须完成，顺序不限。

验收：

- `pytest` 全量通过。
- docs/apis 更新。
- 无 `required_milestone` / `optional_milestone` 算法语义残留。

### Phase 2：不确定性和权重诊断

目标：废弃旧不确定性公式，建立逐维置信度/不确定度，并把动态权重简化为低分、高不确定维度优先。

任务：

1. 删除旧 `compute_uncertainty(...)` composite 公式，移除 `top2_score`、`u_margin`、`u_threshold`、`u_missing`、`u_conflict`。
2. 在 `StageEvaluationResult` 中新增一等字段 `dimension_confidence` / `dimension_uncertainty`，删除全局 `uncertainty` / `judge_confidence`。
3. cheap 层用结构化规则来源计算逐维 confidence；hard fail / missing 不再被视为不确定。
4. standard / expensive 层改为离散 score anchor：standard 默认单次 judge + token probability，不支持 logprobs 时退回 K=3；expensive 固定每个 expensive 维度独立 K=3，用 agreement/entropy 估计 `dimension_confidence`。
5. 动态权重改为指数乘法公式：`raw_next_weight_d = current_weight_d * exp(alpha * (1 - score_d) + beta * dimension_uncertainty_d)`，再归一化。
6. 加 `weight_update_diagnostics`。

验收：

- report / dashboard 面板不再展示全局 `uncertainty` / `judge_confidence`，改为展示各维度 score、confidence、uncertainty。
- metadata 不再出现固定 `top2_score=0.0`、固定 `evidence_conflict=False` 或阈值距离不确定性。
- 单元测试覆盖 hard fail 高置信、LLM 多 pass 分歧高不确定、低分维度增权、高不确定维度增权。

### Phase 3：rubric 一等字段化

目标：让 judge 的评分标准来自 context JSON，且只包含本次需要评估的维度。

任务：

1. 新增 rubric 定义模块。
2. `build_judge_prompt(...)` 支持目标维度集合，但 prompt `context_json` 中不需要单独暴露 `requested_dimensions`。
3. `required_output` 支持 partial dimensions。
4. standard prompt 改为维度组评估。
5. LLM payload 校验支持 partial dimension scores。

验收：

- standard 可只评估 `["tool_quality", "recovery"]`。
- prompt context 中只出现这两个维度的详细 rubric。

### Phase 4：expensive 逐维专项评估

目标：恢复“不同维度不同级别”的动态策略。

任务：

1. 复用 `EvaluationPolicyState.dimension_levels` 做逐维分组，不新增与其重复的持久化计划对象。
2. policy 更新不再通过 `effective_level=max(...)` 调度。
3. expensive templates 拆到 `judge/expensive/`。
4. expensive judge 对 expensive 维度集合逐维调用。
5. 合并 cheap/standard/expensive partial score。

验收：

- 某一维 expensive 不会导致所有维度都 expensive。
- expensive 单维 prompt 只输出该维分数。
- 最终报告仍包含完整七维。

### Phase 5：constraint goal 与 prompt evidence 简化

目标：减少 LLM 被 milestone scorer 复杂字段干扰。

任务：

1. 从 `stage_goal_semantics` 生成 constraint goal。
2. context 中用 `constraint_checks` 替代 `structured_milestone_evidence`。
3. 如需 LLM 生成，扩展 stage goal generation schema。
4. prompt 明确 steps 是主要行为证据。

验收：

- prompt context 不再默认暴露 operator/namespace/actual_summary。
- 每条 constraint check 有自然语言目标。
- LLM 评估 evidence 优先引用 steps。

## 7. 外部参考来源与当前实现关系

以下来源只能作为设计支撑，不能倒推证明当前实现已经合理：

1. ToolSandbox: A Stateful, Conversational, Interactive Evaluation Benchmark for LLM Tool Use Capabilities  
   https://arxiv.org/abs/2408.04682  
   支撑点：stateful tool execution、intermediate/final milestones、arbitrary trajectory 动态评估。

2. τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains  
   https://arxiv.org/abs/2406.12045  
   支撑点：动态用户交互、domain-specific rules、工具/API 与最终数据库状态评估。

3. G-Eval: NLG Evaluation using GPT-4 with Better Human Alignment  
   https://arxiv.org/abs/2303.16634  
   支撑点：LLM-as-a-Judge 使用明确 rubric / form-filling；不支撑当前“粗 rubric + 全维输出”的做法。

4. Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena  
   https://arxiv.org/abs/2306.05685  
   支撑点：LLM judge 可规模化近似人类偏好，但存在位置、冗长、自增强、推理能力等偏差，需要约束 prompt 和可审计证据。

5. Holistic Evaluation of Language Models (HELM)  
   https://arxiv.org/abs/2211.09110  
   支撑点：多指标评估思想；HELM 的七指标与 DynSTEER 七维不同，不能直接声称当前七维来自 HELM。

6. ReAct: Synergizing Reasoning and Acting in Language Models  
   https://arxiv.org/abs/2210.03629  
   支撑点：agent 轨迹中 reasoning/action/tool interaction/exception handling 的重要性。

7. Reflexion: Language Agents with Verbal Reinforcement Learning  
   https://arxiv.org/abs/2303.11366  
   支撑点：错误反馈、反思和恢复行为对 agent 性能的重要性，可支撑 `recovery` 维度。

8. The Multiplicative Weights Update Method: a Meta-Algorithm and Applications  
   https://theoryofcomputing.org/articles/v008a006/v008a006.pdf  
   支撑点：指数/乘法权重更新思想；当前 DynSTEER 权重公式只是 inspired，不是标准 regret-bound 算法。

9. Active Learning Literature Survey  
   https://burrsettles.com/pub/settles.activelearning.pdf  
   支撑点：margin / uncertainty sampling 思想；当前 `top2=0` 没有真实 margin，不应引用它作为实现依据。

10. When Can We Trust LLM Graders? Calibrating Confidence for Automated Assessment  
    https://arxiv.org/abs/2603.29559  
    支撑点：LLM grader 的 confidence 应当被定义为预测与真实标签一致的概率，并用校准指标评估；可支撑 DynSTEER 后续做 judge confidence 校准。

11. Language Models (Mostly) Know What They Know  
    https://arxiv.org/abs/2207.05221  
    支撑点：P(True) / P(IK) 自评置信度在合适格式下可有校准价值；不支持直接采用一次 prompt 里的裸 `judge_confidence`。

12. Teaching Models to Express Their Uncertainty in Words  
    https://arxiv.org/abs/2205.14334  
    支撑点：语言化不确定度可以被训练和校准；DynSTEER 当前不采用 LLM 自报 confidence，只作为“为何不能裸用自报置信度”的反面参考。

13. Self-Consistency Improves Chain of Thought Reasoning in Language Models  
    https://arxiv.org/abs/2203.11171  
    支撑点：多次采样的一致性可以提升推理可靠性；可借鉴为 expensive 多 pass agreement/entropy 的置信度信号。

14. Semantic Uncertainty: Linguistic Invariances for Uncertainty Estimation in Natural Language Generation  
    https://arxiv.org/abs/2302.09664  
    支撑点：开放文本输出的不确定性可按语义等价类估计；可用于 judge evidence/diagnosis 稳定性检查。

15. SelfCheckGPT: Zero-Resource Black-Box Hallucination Detection for Generative Large Language Models  
    https://arxiv.org/abs/2303.08896  
    支撑点：多次采样之间的一致性可用于黑盒不确定性/幻觉检测；可作为 DynSTEER 无 logprobs 场景下的辅助信号。

16. API-Bank: A Comprehensive Benchmark for Tool-Augmented LLMs  
    https://arxiv.org/abs/2304.08244  
    支撑点：工具使用可拆成 planning、retrieving、calling，并通过可执行 API/数据库结果评估；可支撑 cheap `tool_quality` 的规则拆分。

17. Gorilla: Large Language Model Connected with Massive APIs  
    https://arxiv.org/abs/2305.15334  
    支撑点：API call 的正确性可通过函数/API 调用匹配与 hallucination 检查评估；可支撑 cheap 工具名和参数规则检查。

18. ALFWorld: Aligning Text and Embodied Environments for Interactive Learning  
    https://arxiv.org/abs/2010.03768  
    支撑点：agent 计划可同时考虑成功、典型性和效率；可支撑 DynSTEER 把 efficiency 从 progress 中拆出。

19. ALFRED: A Benchmark for Interpreting Grounded Instructions for Everyday Tasks  
    https://arxiv.org/abs/1912.01734  
    支撑点：长序列、不可逆状态变化任务需要同时关注完成度和动作序列；可作为 efficiency / state consistency 的间接参考。

20. On Evaluation of Embodied Navigation Agents  
    https://arxiv.org/abs/1807.06757  
    支撑点：embodied navigation 中将成功与路径效率分开度量；可借鉴为 DynSTEER 对 step/turn 成本进行相对化评价，而不是固定阈值扣分。

## 8. 我建议优先讨论的决策点

1. 是否接受“所有 milestone 都必须完成”并移除 adapted case 中 `required=false` 的兼容。
2. 七维是否保留，还是合并为更少维度。我的建议是保留七维，但必须补详细 rubric 和来源说明。
3. expensive 是否逐维逐 prompt。我的建议是是，且 prompt 放到 `prompt/templates/judge/expensive/`。
4. standard 是否也只输出目标维度。我的建议是是，否则逐维策略仍会被全维输出污染；prompt context 中不必额外放 `requested_dimensions`，以 rubric keys 和 output schema 为准。
5. `structured_milestone_evidence` 是完全移除，还是改成简化 `constraint_checks`。我的建议是改成 `constraint_checks`，保留 scorer 辅助价值，但降低干扰。
6. `dimension_confidence` 固定算法是否接受：cheap 使用结构化置信度；standard 默认单次 judge token probability，不支持 logprobs 时退回 K=3 agreement entropy；expensive 每个 expensive 维度独立 K=3 agreement entropy。我的建议是接受，兼顾置信度质量和调用成本。
7. 动态权重是否接受指数乘法公式 `w_next = w * exp(alpha * (1-score) + beta * uncertainty)`。我的建议是接受，删除 `target/focus`，保留 `alpha/beta` 作为两个清晰强度参数。

## 附录A. 项目中没有把握实现的模块部分

1. 历史 adapted case 的兼容迁移  
   没有完全把握的原因：当前仓库没有实际 `data/{benchmark}/adapted_cases` 样例可核查。若外部已有大量缓存 JSON，移除 `required` 会要求重新生成或写一次迁移脚本。按项目约束我倾向于不做旧接口兼容，但这会影响已有实验资产。

2. expensive 逐维 prompt 的最终 rubric 质量  
   没有完全把握的原因：prompt 需要结合真实失败样例反复调试。仅靠代码静态核查可以确定当前 prompt 不够好，但不能一次性保证新 prompt 的评分稳定性。

3. `dimension_confidence` 的校准质量  
   没有完全把握的原因：当前没有足够历史 run 的人工标签或高可信 oracle 来校准 confidence。cheap 结构化规则可以先给出可解释 raw confidence；standard/expensive 的多 pass agreement 只能说明一致性，不等同于正确性，后续仍需要校准集。

4. 动态权重 `alpha/beta` 默认强度  
   没有完全把握的原因：`alpha=1.0` 与 `beta=1.0` 是首版等权先验，不是论文或实验结论。如果后续运行发现权重过度追逐低分或过度追逐不确定度，需要基于历史 run 调整二者比例。

5. constraint goal 生成是否完全覆盖所有 benchmark  
   没有完全把握的原因：ToolSandbox 的 `stage_goal_semantics` 覆盖较清晰，但其他未来 benchmark 的私有约束可能缺少足够语义。需要 adapter 层承担语义映射责任。

6. partial dimension status 合并规则  
   没有完全把握的原因：不同维度对阶段 pass/fail 的权力不同，例如 safety/progress 应能覆盖整体状态，但 efficiency/interaction 是否覆盖需要和评估目标共同确定。建议在代码落地前先确认 status aggregation policy。
