# DynSTEER 实验代码修改细化方案

## 1. 方案范围

本文档是 [2026-09-15-DynSTEER跨Benchmark主实验与介入实验方案.md](2026-09-15-DynSTEER跨Benchmark主实验与介入实验方案.md) 的代码落地方案，只描述修改，不落地实现。

实验文档已删除 `no_frontier_stop` 消融臂。因此本次不新增 `stop_on_frontier_stagnation` strategy 字段，也不新增 `dynsteer_replay_no_frontier_stop` 方法；ready-frontier 无进展 stop 在所有 replay 和在线 DynSTEER 臂中保持现有默认启用状态。

修改目标只有四类：

1. 让 `no_minefields`、`no_milestone_graph`、`no_policy_stop` 三个消融臂在同一 experiment 内有唯一输出身份。
2. 支持 ToolSandbox 在线 guided intervention，并在 stop/guided 后保留 native task completion。
3. 让 Default、replay、online arm 的时间与 token 成本可解释，区分真实 0、分摊 0 和缺失 null。
4. 输出实验文档要求的 DS audit、saved progress、task completion、消融 audit 和介入显著性指标。

不新增旧接口兼容层、通用策略解释器或额外中间层；所有开关直接进入现有配置、适配和评估链路。

本版已对照本地只读源码核查关键兼容点：`../ToolSandbox` 和 `../AgentCompass`。核查结果直接写入第 4、6 节和附录；仍然不修改这两个仓库，也不在 DynSTEER 中为外部仓库新增补丁层。


### 4.2 新增 `dynsteer/evaluate/intervention.py`

该文件只提供一个公共函数：

```python
def build_intervention_message(
    task_case: TaskCase,
    decision: RuntimeEvaluationDecision,
    state: RuntimeEvaluationState,
) -> str:
```

实现规则：

1. 只读取 `task_description`、已物化 stage goal、当前 stage status/score、ready frontier 的 id/name、当前 decision 的结构化诊断和 match attempt 白名单 evidence。
2. 禁止读取 expected state 原文、gold patch、hidden verifier、完整 milestone constraints 或未来轨迹。
3. 消息以 `[DynSTEER intervention]` 开头，明确说明这是过程诊断提示，不改变任务目标。
4. 输出长度截断到固定上限，例如 1200 字符，避免长诊断进入 agent 上下文后放大成本。
5. 不在这里写日志和 metadata；调用方 `DynSTEEREvaluator` 统一记录，避免同一事件两处落盘。

### 4.3 `dynsteer/adapter/base.py`

`BaseBenchmarkHarness` 新增继承接口：

```python
def send_guidance(self, session: object, message: str) -> None:

        raise ValueError("session 不能为空")
```

该默认实现就是接口契约，不是死代码。非 ToolSandbox benchmark 在误配置 guided method 时必须显式失败，而不是静默降级成 stop。

### 4.4 `dynsteer/adapter/toolsandbox/harness.py`

源码核查结论：`BaseRole.add_messages(messages)` 是公开写入 API，内部调用 `ExecutionContext.add_to_database(DatabaseNamespace.SANDBOX, ...)` 并自动分配连续 `sandbox_message_index`；`Message.visible_to` 默认为 `[sender, recipient]`，可显式收窄。agent 的 `to_openai_messages()` 只把 `USER -> AGENT` 转为普通 OpenAI user 消息；`SYSTEM -> AGENT` 虽会转为 system 消息，但 `OpenAIAPIAgent.respond()` 看到最新 sender 为 `SYSTEM` 时会直接返回，因此不能作为最后一次追加消息来触发 agent。

覆盖 `send_guidance()` 和 `_append_guidance_message()`：

1. 先校验 `ToolSandboxSession`、非空 `message.strip()`、`conversation_active` 仍为 true、当前 `sandbox_message_index` 未达到 `initial_max_sandbox_message_index + max_messages`。
2. `_append_guidance_message()` 加载 `tool_sandbox.roles.base_role.BaseRole`、`tool_sandbox.common.message_conversion.Message` 和 `RoleType`，在当前 context 上追加：

```python
Message(
    sender=RoleType.USER,
    recipient=RoleType.AGENT,
    content=message.strip(),
    visible_to=[RoleType.AGENT],
)
```

   这是 ToolSandbox 支持的“外部隐藏介入轮”：它进入 agent 的 OpenAI `user` prompt，但 user simulator 的 `filter_messages()` 会排除该消息，不会看到或回应它。
3. content 直接保留 `[DynSTEER intervention]` 前缀的纯文本；不伪造 openai tool call 字段，不加 JSON 包装。
4. 调用顺序为：`_set_current_context(session.context)` -> `BaseRole.add_messages(...)` -> `session.context = _get_current_context()`。写入后用 `context.max_sandbox_message_index` 校验索引确实前进，并把 `session.last_sandbox_message_index` 更新为该新值，防止下一次 `advance_case()` 把 guidance row 重复转成步骤。
5. 不直接修改 Polars DataFrame 私有列，不绕过 `BaseRole` 调用 `ExecutionContext.add_to_database()`；模块加载复用现有 `load_toolsandbox_module()`。

### 4.5 `dynsteer/evaluate/evaluator.py`

修改 `_apply_live_decision()` 签名，把当前配置传入：

关闭该开关的旧 online `dynsteer_evaluate` 不进入这段分支，不调用 `default_result_from_session()`，也不新增 `native_evaluation_seconds`、`native_evaluation_*` token、`native_default_result` 或 `native_score` 字段，完全保持当前 online evaluate 行为。开关开启时，这次调用在 `_build_runtime_metrics()` 之前执行，用 `time.perf_counter()` 包裹调用本身；构造 runtime metrics 后把 `native_evaluation_seconds` 和从 `default_result.metrics` 读取的三个 `native_evaluation_*` token 字段并入 runtime metrics。介入实验的 `dynsteer_evaluate` stop 配置和 `dynsteer_evaluate_guided` 配置都显式设置 `collect_online_native_score=true`，因此两者的 native 数据可与 agent 执行时间分开。

## 6. 成本、时间与 ACTF 修正

### 6.1 明确原生评估 token 为真实 0

源码核查结论：ToolSandbox `Evaluation.evaluate()` 只读取 context 数据库并计算 milestone/minefield similarity，不调用 LLM；SWE-bench Pro 和 SkillsBench verifier 也是容器内脚本验证。因此三个 benchmark 的 native evaluation token 不是“缺失”，而是真实 0。

修改三个 harness 的 `BenchmarkDefaultResult.metrics`，保留现有三个 0 token 字段，并新增同一来源标记：

```python
"native_evaluation_token_source": "deterministic_native_verifier"
```

ToolSandbox metrics 同时保留 `turn_count` 等 native 字段；SWE-bench Pro 保留 returncode/status，SkillsBench 保留 test returncode/status。`write_default_case_outputs()` 现有 `native_evaluation_token_available=True` 判断保持不变，不重复新增第二套可用性字段。

### 6.2 新增 `dynsteer/adapter/toolsandbox/utils/usage.py`

新增一个小型 usage recorder，只服务于 ToolSandbox agent provider。源码确认 ToolSandbox 的 OpenAI agent/user 和 Anthropic agent 都是非流式调用；provider response 是可靠 usage 读取点。该 recorder 不包装业务 role，只挂在 provider SDK 的 `DefaultHttpxClient` 上：

```python
@dataclass
class ProviderUsageDelta:
    prompt_tokens: int | None
    completion_tokens: int | None
    total_tokens: int | None

class ProviderUsageRecorder:
    def record_openai_response(self, response: httpx.Response) -> None: ...
    def record_anthropic_response(self, response: httpx.Response) -> None: ...
    def take_delta(self) -> ProviderUsageDelta | None: ...
    def summary(self) -> JsonObject: ...
```

实现规则：

1. `record_openai_response()` 只读取 `usage.prompt_tokens`、`usage.completion_tokens`、`usage.total_tokens`；`record_anthropic_response()` 只读取 `usage.input_tokens`、`usage.output_tokens` 并令 `total = input + output`。
2. 每次 response hook 记录最小结构 `(available, prompt_tokens, completion_tokens, total_tokens)`；不保存请求体、响应正文、URL、header 或 provider cost/cache 字段。
3. `take_delta()` 消费自上次调用以来的 responses：没有新 response 时返回三项 0 且 available true；全部有 usage 时求和；任一 usage 缺失或 JSON 不可解析时返回 `None`，只增加 `missing_response_count`。
4. `summary()` 输出累计 prompt/completion/total tokens、request count、usage response count、missing response count 和 `available`。`available` 表示所有 agent provider response 都有完整 usage，而不是表示没有 provider 调用。
5. HTTP hook 解析异常不得吞成静默缺数：记录结构化 warning 和 missing count，但继续让本次 provider 调用完成；usage 可用性在 case 结束时如实汇总。
6. hook 必须是纯观察者：不修改 request/response、header、retry、timeout 和 redirect；解析异常在 hook 内捕获，不改变 provider 调用结果。

### 6.3 `dynsteer/adapter/toolsandbox/utils/roles.py`

修改 role client 构造，并保证旧配置零行为变化：

1. `get_agent_factory()` 接受可选 `usage_recorder`，`get_user_factory()` 不接收 recorder。
2. `_role_factory()` 和 `_build_role_factory()` 透传 recorder。
3. `recorder is None` 时，`_openai_client_from_config()` 和 `_anthropic_client_from_config()` 必须维持现有构造分支，不创建自定义 `httpx.Client`。
4. `recorder` 存在时，必须使用 provider SDK 暴露的 `DefaultHttpxClient`（`openai.DefaultHttpxClient` / `anthropic.DefaultHttpxClient`）创建带 response event hook 的 client，禁止裸 `httpx.Client`。裸 client 会把 OpenAI/Anthropic SDK 默认超时、连接池和 `follow_redirects=True` 替换成 httpx 默认值，可能显著改变既有任务执行。若 client config 指定 `timeout_seconds`，将同一个 `httpx.Timeout` 传给 `DefaultHttpxClient`；未指定时保持 SDK 默认 timeout。
5. 只给 agent role 挂 hook；user simulator usage 不计入 agent tokens。

不支持 usage hook 的 provider（例如当前 ToolSandbox Gemini role 使用 pass-through client）输出 `available=false`。实验模型矩阵全部使用 OpenAI-compatible / Anthropic provider，不依赖该路径。

### 6.4 `dynsteer/adapter/toolsandbox/harness.py`

`start_case()` 只有在 `config.metadata.get("capture_agent_usage") is True` 时创建 `ProviderUsageRecorder`，用它构造 agent role，并把 recorder 保存到 `ToolSandboxSession`；否则 recorder 为 `None`，role 构造与当前实现一致。既有配置不写该字段，因此不会开启新的 HTTP hook。

`advance_case()` 中：

1. 调用 `_advance_native_session()` 前记录 usage snapshot。
2. 调用后调用 `recorder.take_delta()`。
3. delta 可用时，把该批次 `total_tokens` 写入本批次第一条 `AGENT -> EXECUTION_ENVIRONMENT` 或 `AGENT -> USER` step 的 `cost.tokens`；同一批次内其余 raw step 的 token 写 0。
4. delta 缺失时，本批次 agent outbound 的 token 保持 `None`，不把部分批次当作完整前缀。
5. user simulator 和 environment step 的 agent-ledger token 一律为 0；这不是消耗为 0，而是明确不归属 agent backbone。
6. 出现“delta 非零但本批次没有 agent outbound”的异常状态时，计入 recorder summary 的 missing response count，并使该 case `available=false`；不把它摊到其他步骤。

这样现有 `prefix_trajectory_cost()` 可以继续按 raw step 前缀求和，不需要新增第二套前缀 token 聚合逻辑。

`metrics_from_session()` 必须合并而不是覆盖既有返回值：先返回 `{"native_evaluation_skipped": True}`；recorder 存在时再追加 `agent_usage=recorder.summary()`。`advance_session_trajectory()` 现有逻辑会在每个批次后更新 `trajectory.metrics`，因此第 6.6 节的 `build_runtime_metrics()` 可以直接读取该对象。不另建 recorder-to-runtime 的复制层。

### 6.7 `dynsteer/adapter/agentcompass/trajectory.py`

源码核查结论：AgentCompass `TrajMetric` 稳定暴露 `prompt_tokens_len`、`completion_tokens_len`、`llm_infer_ms`、`env_action_ms`，但 ACTF 不存在独立 `total_tokens`；DynSTEER 在转换层由前两项求和。SWE-bench Pro 常用 mini-SWE-agent 轨迹转换会从原始 response usage 填充 prompt/completion，并推导 LLM/environment latency。字段是否出现仍取决于 provider response 和所选 harness，因此缺失必须保留 null。

修改 `convert_actf_steps()` 的成本归属：

1. 一个 ACTF native step 的 LLM token 和 LLM latency 只归属一个代表 converted step：
   - 有 tool calls 时，第一个 tool call 是代表；
   - 无 tool calls 且有 assistant content 时，final message 是代表。
2. 同一 native step 派生的其余 converted step，对应 token/LLM latency 写 0，表示“确认不属于该 raw step”。
3. environment latency 只归属第一个成功配对 observation；同 native step 的其他 observation latency 写 0。
4. 如果 native metric 本身缺失 token 或 latency，代表 step 和派生 step 都保持 `None`；不得用 0 填充缺失。
5. 首个 native step 之外转换出的 user message，token 和 latency 固定为 0，不进入 agent backbone ledger。
6. `_cost()` 继续只校验 prompt/completion 分别存在时的非负语义；只有其中一项存在、另一项缺失时视为该 native step token 缺失（返回 `(None, ...)`），不用半个 usage 求和。

不新增独立 ACTF 成本汇总函数；继续复用 `_trajectory_token_summary()`、`prefix_trajectory_cost()` 和 `build_replay_timing_metrics()`。

### 6.8 `dynsteer/experiment/metrics.py`

`_result_cost()` 保持四类账目：

| 账目 | Default | Replay | Online DynSTEER |
| --- | --- | --- | --- |
| agent time | `execution_total_seconds` | `default_prefix_execution_seconds` | `execution_total_seconds` |
| DynSTEER evaluation time | null | `elapsed_seconds` | `elapsed_seconds - agent_time`，无法扣减时 null |

## 7. 统计指标

### 7.1 SciPy 依赖

`pyproject.toml` 将 `scipy==1.13.1` 从 `[tool.uv.optional-dependencies.toolsandbox]` 移到 `[project.dependencies]`。原因：`dynsteer.experiment.metrics` 是核心汇总模块，介入实验和消融实验都依赖 Wilcoxon 与 exact binomial test，不应依赖可选 benchmark extra 才能导入。

### 7.2 `dynsteer/experiment/metrics.py`

新增一个通用私有 helper 和五个公共输出：

```python
def _paired_differences(
    left: Sequence[ExperimentCaseResult],
    right: Sequence[ExperimentCaseResult],
    value_getter: Callable[[ExperimentCaseResult], float | None],
) -> tuple[list[float], int]

def saved_progress(results: Sequence[ExperimentCaseResult]) -> JsonObject
def paired_model_audit(results: Sequence[ExperimentCaseResult]) -> JsonObject
def paired_group_audit(results: Sequence[ExperimentCaseResult]) -> JsonObject
def bootstrap_paired_delta(
    left: Sequence[float],
    right: Sequence[float],
    *,
    seed: int = 202608,
    samples: int = 10000,
) -> JsonObject
def exact_mcnemar(
    results: Sequence[ExperimentCaseResult],
    *,
    left_method: ExperimentMethod,
    right_method: ExperimentMethod,
    threshold: float = 1.0,
) -> JsonObject
```

实现规则：

1. 配对统一使用现有 `_pair_key()` 语义：`(benchmark, model_id, repeat_index, case_id)`。跨实验聚合时调用方先在 result identity 中加入 experiment group，不在 helper 内猜测。
2. `_paired_differences()` 只保留两侧均有有效值的 key，并返回缺失配对数。
3. Wilcoxon 使用 `scipy.stats.wilcoxon(..., zero_method="wilcox", alternative="two-sided")`；所有差值为 0 时输出 `p_value=1.0`、`all_zero_differences=True`，不传播 SciPy warning。
4. `saved_progress()` 只对 replay method 且 `termination_code` 非空的 case 计算 `1 - stop_step / default_total_step`；输出 stopped count、stop rate、均值、中位数、p10/p90/p95、invalid count 和 per-model 分布。
5. `paired_group_audit()` 对消融 method 与 full method 配对，输出 score delta、Wilcoxon、saved progress delta 和 bootstrap CI。`no_policy_stop` 的 saved progress delta 为 null，并写 `saved_progress_applicable=false`。
6. `exact_mcnemar()` 构造两 method 的 completed/failed 列联表，只对 discordant pairs 调用 `scipy.stats.binomtest(k, n, 0.5).pvalue`；discordant count 为 0 时 p=1。
7. bootstrap 使用 `numpy.random.default_rng(seed)` 和 percentile CI；不创建全局 random state。

`paired_model_audit()` 输出 DS 之外的 model-pair Wilcoxon audit，不修改现有 `discriminability_score()` 公式。`write_metric_tables()` 的 `metrics` 增加：

```text
"saved_progress"
"paired_model_audit"
"paired_group_audit"
```

介入实验的 McNemar 可以由后处理脚本或实验报告层调用 `exact_mcnemar()`；不把它硬编码进主实验 generic metrics 的固定 method 组合，避免 metrics 模块依赖某个具体实验分组名。

## 11. 既有 ToolSandbox 结果兼容性

本方案不得改变既有 ToolSandbox 方法的执行语义。落地时按以下边界验收：

1. 旧配置零开关：未写 `capture_agent_usage=true` 和 `collect_online_native_score=true` 的配置不创建 recorder、不替换 HTTP client、不调用 online native evaluation；provider 请求、重试、超时、redirect、轨迹、native score 和 stop 决策路径保持现状。
2. 默认策略不变：`use_milestone_graph`、`use_minefields`、`max_interventions` 的默认值不改变现有 `default`、`dynsteer_replay`、`dynsteer_replay_static`、`dynsteer_replay_static_routing`、`dynsteer_replay_static_weighting` 和 `dynsteer_evaluate` 行为；新开关只被新 enum 消融/引导方法读取。
3. ready-frontier stop 不变：不新增或修改 `stop_on_ready_frontier_no_progress` 默认值，也不删除 `no_frontier_stop` 以外的现有 stop 路径。
4. guided 隔离：`send_guidance()` 只由 `dynsteer_evaluate_guided` 调用；其他方法不进入消息写入分支。
5. native evaluation 只读：online stop/guided 调用 `Evaluation.evaluate()` 只新增 native score 字段；不得在评估前后修改 `ExecutionContext` 状态或 SANDBOX rows。
6. 磁盘产物隔离：`use_milestone_graph=False` 使用独立 adapted case 文件；程序不重写、不回填既有 ToolSandbox trajectory、raw summary、summary 和 metrics。已有结果目录只允许读取，禁止以 force 模式重新生成作为兼容性验证。
7. schema 兼容：`ExperimentCaseResult.native_score` 等新增字段必须有默认值；读取旧 JSON 时缺失等价于 null，不允许要求旧结果重新生成。

兼容性验收使用同一历史配置在临时 results/runs 目录做 smoke replay，不改源结果目录；历史配置必须保持两个观测开关关闭。对比标准是：step 序列、stop step、DynSTEER score 和 termination code 完全一致；历史上已存在 native score 的输出该值也必须一致，旧 online 输出没有 native score 时继续保持缺失。新增 diagnostic 字段允许出现，但不得参与旧指标计算。usage/time 只在显式开启 capture 的新实验中比较，不与关闭 capture 的历史结果混池。

## 附录A. 项目中没有把握实现的模块部分

1. ToolSandbox 引导消息语义：写入 API 已确认为 `BaseRole.add_messages()`；`ExecutionContext.add_to_database()` 自动分配 SANDBOX index。原方案的 `SYSTEM -> AGENT` 不可直接触发 agent，因为上游 `respond()` 会跳过最新 sender 为 SYSTEM 的批次。方案已改为 `USER -> AGENT` 且 `visible_to=[AGENT]`。剩余不确定点只在实际模型 provider 对 tool result 后接 user 消息的兼容性；实现时先做单 case pilot，若 provider 拒绝该序列，guided case 记录 implementation failure，不得改用泄漏给 user simulator 的可见用户消息。

2. ToolSandbox provider usage 覆盖率：OpenAI-compatible 和 Anthropic 的当前源码路径均为非流式调用，可通过 provider SDK `DefaultHttpxClient` 的 response event hook 读 response usage。Gemini/pass-through 和其他特殊 client 不注入 recorder，或 recorder 无法解析时如实输出 `available=false`。实验模型矩阵只使用 OpenAI-compatible / Anthropic，残余风险主要是 provider 网关未返回 usage。

3. 空 milestone graph 在 AgentCompass 上的稳定性：现有空图 whole-trajectory 路径主要由 ToolSandbox 场景验证，SWE-bench Pro 和 SkillsBench 的空图 stage goal、finish judge 和异常率仍需 pilot 验证。若该臂大量报错或 score 缺失，应记录为 implementation failure，不得解释为 milestone graph 无贡献。

4. ACTF 成本字段覆盖：不同 AgentCompass harness 可能缺少 prompt/completion token、LLM latency 或 environment latency。方案只规范化“一次归属、派生为 0、真实缺失为 null”，但无法在没有真实 detail 抽样的情况下保证三个 benchmark 成本字段都有数据。

5. Guided intervention 的因果解释：引导消息可能通过额外提示、额外探索时间或 user simulator 反应改变结果。三臂设计和配对检验能控制主要差异，但不能把提升普适化为所有 prompt 或所有 benchmark 的因果效应。
