# Harness中Agent的动态评估

## 1. 研究动机 / Motivation

- 现实场景中刚需Agent处理的工作往往是长规划、长程执行的任务，例如项目级别代码的编写与调试（Claue Code / CodeX）、深度研究Agent的调研与研究计划拟定（ChatGPT的DeepResearch）等，仅评估最终交付成果难以全面衡量Agent的任务执行能力，也无法针对性地对模型本身或对Harness某个模块展开优化，极大降低优化效率、抬升优化成本。

- 现有轨迹评估工作仍主要依靠人工或模型构建的benchmark，通过比对参考轨迹等方法给出工具选择与调用是否正确、步骤是否合理的评估结果。但现有评估仍有挑战未解决：

  - **相对死板评估结果：**现有方法主要依靠为任务针对性构建或收集的一条执行轨迹作为参考进行比对，而实际Agent执行过程是动态且多样化的，benchmark中的“标准轨迹”的合法性不唯一，导致基于“标准轨迹”的评估结果相对死板，存在扼杀Agent给出更优方案可能的风险。例如，Anthropic在博客《[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)》提及他们发现Agent经常找到设计者没预料到的有效方法。

    此外，benchmark也存在被定向优化的风险，例如LLM 在 SWE-bench Verified 上的表现提升非常快，仅一年就从原来的 40% 提到了 80% 以上（2024年12月o1-preview表现41.3%，2025年11月Claude Opus 4.5就达到80%了）。

  - **滞后且静态的评估：**现有方法需要完整的Agent执行轨迹进行评估，给出的评估结果为针对单次任务执行全程的统计性结果，一方面是缺乏针对性对错误环节进行细粒度定位与详细分析的解决方案，需要人工复核；另一方面缺乏动态的、实时的对Agent执行过程的跟踪评估，评估滞后于任务执行，任何评估与优化都必须承担Agent长程执行的全部代价。

- 因此，有必要研究一种能够**动态地形成测例、动态跟踪并评估Agent执行过程的评估框架** ===> 不仅作为验收评估器、同时作为中间执行的跟踪器与控制器

## 2. 相关工作 / Related Work

### 2.1 汇总

**评估对象Agent类型（目前常用Agent）：**编码Agent、对话Agent、研究Agent、计算机操作（交互）Agent

**评估维度：**

- **正确性：**任务完成率、答案准确率、工具调用准确率、幻觉率、……
- **效率：**端到端平均响应延迟、Token消耗、工具调用次数、重试率、……
- 安全性：越权操作率、注入攻击成功率、拒绝率、……
- 用户体验：用户满意度、任务放弃率、澄清次数、回访率、……

**评估层级：**单步评估 -> 轨迹评估 -> 任务完成评估

#### 2.1.1 单步评估 (Step-level)

单步的工具选择、参数正确性、输出格式（现有工作中，轨迹评估一般覆盖单步评估）。通过单元测试、格式校验、LLM评分等。

#### 2.1.2 轨迹评估 (Trajectory-level)

单次任务执行的步骤顺序、冗余操作、路径效率等。通过轨迹对比、LLM-as-a-Judge、人工审核等实现。

BFCL 将函数调用评估推进到多步与结构校验；AgentRewardBench 直接评估“自动评估器能否判断 Web Agent 轨迹质量”；TRAJECT-Bench 聚焦工具轨迹中的工具选择、参数化与依赖顺序；AURA 强调用户满意度不仅取决于终态，也取决于中间交互行为；DeepRed 通过 checkpoint partial credit 将长程执行过程转化为可量化轨迹进展；Claw-Eval 则结合执行轨迹、审计日志与环境快照进行可追踪评估。

总体来看，轨迹评估更适合定位 harness、planner、tool router、memory 与 verifier 等模块中的问题。但是，目前的轨迹评估也面临如下问题和挑战：

- **评估结果较为死板**：目前的轨迹评估依赖预先合成的轨迹benchmark（收集或者依靠人工/模型从工具池合成轨迹），通过参考轨迹与Agent实际轨迹比对，可能评估结果相对死板（合法路径不唯一）
- **benchmark构筑成本高昂**：benchmark构建以及评估规则和标准依托人工构建（BFCL、Claw-Eval），成本较高。
- **评估粒度较粗**：轨迹评估结果目前主要是宏观的统计结果，较少能对错误环节进行细粒度定位与详细分析（并非单纯地定位执行错误（依靠单步评估即可），而是执行步骤逻辑中出错的点位）。

#### 2.1.3 任务完成评估 (Task-level)

评估最终Agent执行完成任务后是否达成了预期目标、用户满意度如何、是否满足业务指标。通过A/B测试、用户调研、自动化验收方法实现。目前大部分benchmark都是关于各种场景、各类任务的完成情况的验收与评估。

早期 benchmark 多以任务级成功率、终态环境状态或答案正确性作为核心指标，例如 AgentBench、GAIA、WebArena、WorkArena、OSWorld、AndroidWorld 与 SWE-bench。此类方法能够回答“Agent 最后是否把任务做成”，并通过环境状态、数据库状态、测试用例或任务产物进行客观验证。

2025–2026，结果评估开始进一步细化：PaperBench 通过层级 rubric 评价科研复现产物；Workspace-Bench 将评测扩展到大型工作区、多文件依赖与复杂交付；ST-WebAgentBench 则强调“完成任务但违反政策”不能算真正成功。

目前存在的挑战：

- **benchmark泄露与过拟合风险上升**：公开任务池、固定题源与 leaderboard 压力可能导致 benchmark 很快饱和。
- **任务场景复杂，评测成本高**：Agent面向的任务场景复杂多变，往往针对不同任务场景需要设计和采用不同指标、搭建不同的环境/沙盒，成本高昂、**需要特事特办**。

#### 2.1.4 动态评估

基于预构建的benchmark对Agent的任务完成能力或更细粒度的执行轨迹进行评估，存在数据泄露与过拟合、评估结果死板、评测成本高昂的问题。那么研究如何动态更新或筛选测例，更进一步研究如何基于任务阶段、已有结果判定“何时评、评什么、怎么评”就具有明确必要性。

近两年开始有Agent动态评估相关研究。例如ToolSandbox 面向真实场景研究交互式评估，引入了针对任意轨迹的中间里程碑与最终里程碑动态评估；Agent-Testing Agent 会根据前序测试结果与 judge feedback，自适应地产生更有针对性的后续测试；Efficient Benchmarking of AI Agents 则从评测成本角度提出，只选择高信息量任务子集即可较好维持 agent 排名稳定性。

目前调研到的文献存在的问题：

- 主要聚焦在测例的动态生成上，对于动态轨迹的评估比较简单（ToolSandbox是关注到轨迹的汇合点（必须做的里程碑）上，但这只涉及完成率和轨迹是否合理的最简判断）
- 目前调研到的评估工作（包括交付验收和轨迹评估），主要是任务完成后的验收与反馈。在实际使用中意味着Agent需要完整执行一次任务，才能基于评估反馈进行重试或调优 ===> 能否在执行过程中进行动态跟踪与纠偏？（例如在harness中，不仅作为验收评估器、同时作为中间执行的跟踪器与控制器）

## 3. 方案 / Methodology

**可能标题：**

- **DynaSTEER: Dynamic Stage-wise Trajectory Evaluation and Execution-time Review for Agents**
- ……



**通过基于待评估的任务人工/自动归纳的轨迹阶段节点（若Agent执行该任务必须执行完成的操作节点），划分Agent执行的阶段，进行阶段式评估。**

具体地：

**1. 轨迹的预期评估阶段划分：**

- 基于待评估的任务需求（如搭建项目、调研并给出方案、……），人工/自动归纳出完成该任务时必须执行的操作节点，并给出若干预期参考线路。
  - 初步实验中，尝试人工标注（可采用现有benchmark，例如ToolSandbox的milestone和minefields标注）；
  - 后续实验中，尝试基于人工标注调试一版可自动规划的生成框架。（例如基于任务需求先模拟规划出多条执行路径，然后对这些路径做归纳整理和节点收束，这些路径也可作为粗粒度的参考轨迹）
- 基于这些阶段节点，划分全评估流程的评估阶段
  - 粒度粗一些，避免强制约束Agent执行轨迹到特定路径上、导致Agent创新性和扩展性的缺失

**2. 阶段式动态评估：**

每个阶段节点，对上个节点到该节点中间的评估过程，进行一次结算式评估：

- 对于Agent执行单步，采用当前通用的评估手段（例如对于检索工具，采用通用的precision / recall等指标）
  - 目前评估方法中，评估单步骤动作或工具调用的正确性和质量，常见指标包括：**动作正确率、语义一致性、可执行性**等。
    - [AgentProcessBench](https://arxiv.org/pdf/2603.14465)：针对多工具交互任务的高质量步骤级评估基准。提出对每个助手步骤进行“正确(+1)、中性(0)、错误(-1)”三类标注，并定义StepAcc和FirstErrAcc两种指标，评估对每步正确性和首个错误定位能力
      - 由模型扮演“严格公平的轨迹标注员”，输入任务描述、工具定义、完整轨迹、标注规则，输出`轨迹步骤index : 步骤标签`的字典。步骤标签包含：+1（事实正确且推进任务）、0（中性/探索性步骤，合理但对任务进展影响有限或不确定）、-1（事实错误、工具误用、违反约束或让任务偏离）
      - 两个指标评判模型标注的好坏：（这个指标无法用于轨迹自身质量的评判）
        - Step Accuracy / StepAcc：轨迹中标注与人工标注一致的占比
        - First-Error Accuracy / FirstErrACC：标注第一个-1步骤是否与人工一致。
    - [STeCa](https://arxiv.org/pdf/2502.14276)：出Step-level Trajectory Calibration，通过对探测到的次优动作进行校准，生成“校准”轨迹用于强化训练。STeCa用 Monte Carlo sampling 估计每一步动作的“未来成功概率”，以此锚定每个步骤的价值。**（缺陷：多次模拟轨迹，计算开销巨大）**
      - 在执行了当前动作后，从当前历史继续 rollout 多次，最终成功率越高，这个动作的 step reward 越高
      - 经验假设：在正确轨迹中，单步step reward应单调上升（即步骤的未来成功率会越来越高）==> **用于检测步骤是否偏离**
  - **目前单步骤评估，不基于LLM的效果较差，基于LLM的开销巨大，在阶段式评估中不适宜长时开启** 
    - **===> 可能考虑，仅在前一阶段表现较差的维度启用单步骤的细粒度评估，以获取更精确的缺陷分析。**
- 对当前阶段全部步骤，基于参考轨迹进行一次整体评估，包括轨迹是否存在冗余（相较参考轨迹增加的步骤数量、不必要的中间结果或状态数量等等）、执行结果是否符合任务需求、轨迹偏离程度等
  - 评估维度：
    - 当前阶段任务是否正确执行、执行效率（所需资源、时间、步骤数、工具调用数量等）、工具调用合理性（成功调用工具次数、动作精确匹配率等，可能需要通过参考轨迹进行比对）、状态一致性（各单步骤“内部状态”是否正确反映用户意图）

  - 通过预设阈值判定每一个维度的执行结果是否可以接受。
    - 可以为各维度赋予一个权值，计算各维度加权总分作为阶段性评估分数。初始权值为平均 / 人工调整 （或者尝试基于任务自动赋予？）
  - 若不可接受，提前终止评估；若可接受，基于各维度结果调整权值，分数较低的维度增大权值，并且后续评估中该评估维度可能需要采用更细粒度的评估工具进行评估（即优先关注做的不足的地方），形成动态评估策略。

### 4.1 如何验证评估的有效性

| 验证目标          | 现有工作中的常见做法                                         | 可能的的验证方案                                             |
| ----------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 评估器稳定性      | [CheckEval](https://arxiv.org/abs/2403.18771) 比较 evaluator 间一致性与评分方差；[τ-bench](https://arxiv.org/abs/2406.12045) 用 `pass^k` 衡量重复试验可靠性 | 比较同一任务多次运行下的评分方差、Judge 自一致性和跨 Judge 一致性 |
| 区分度 / 排序保真 | [Efficient Benchmarking of AI Agents](https://arxiv.org/abs/2603.23749) 关注 reduced suite 是否保持模型排序；[ATLAS](https://arxiv.org/abs/2511.04689) 用信息量高的题目提升测量效率 | 比较动态评估与全量评估在 Spearman / Kendall 排序上的一致性；比较相近模型与不同 scaffold 是否更容易被区分（不同模型结果的方差是否更大） |
| 低成本有效性      | [Efficient Benchmarking of AI Agents](https://arxiv.org/abs/2603.23749) 直接考察成本下降与 rank fidelity 之间的 trade-off | 报告 tokens、wall-clock、工具调用次数、环境执行次数、人工复核量，并计算“单位成本带来的排序保真” |
