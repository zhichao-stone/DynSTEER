# DynSTEER 完整实验方案

## 1. 方案目标

本方案基于截图中的判断，围绕 DynSTEER 的阶段式动态轨迹评估能力设计一组完整实验。核心目标不是单纯证明“评测更省钱”，而是证明 DynSTEER 在以下方面有明确价值：

1. **评估更可靠**：相对终态验收或整轨迹一次性 SOTA Judge，DynSTEER 能更准确识别阶段完成、状态一致性、工具质量和 minefield 风险。
2. **区分度更强**：能把不同能力层级的 Agent 模型分得更开，尤其能揭示“最终任务成功率接近，但过程质量不同”的差异。
3. **低成本可用**：在长轨迹场景中，可以用 cheap / standard / expensive 分层调度，降低评估成本，同时保持足够的排序保真和诊断质量。
4. **支持运行期指导**：在 Agent 执行过程中进行动态评估，并验证“带指导”相对于“不带指导”是否提升成功率、减少错误累积或降低无效执行成本。

## 2. 截图信息转译

截图中给出的实验设计要点可以转译为四条实验主线：

| 截图要点 | 实验转译 |
| --- | --- |
| 纯讲效率比较弱 | 效率只作为副指标；主张应放在评估有效性、模型区分度、长轨迹可扩展性和运行期纠偏价值上。 |
| SOTA 的评估方法不一定准 | 需要设置 SOTA 终态 Judge / 整轨迹 Judge 作为对照，比较其与人工标注、benchmark 原生结果、阶段证据的一致性。 |
| 需要效率提升很多 | 报告 token、调用次数、耗时和单位成本排序保真，并在长轨迹分桶上证明成本优势。 |
| 更有差异化 | 不能只报告平均分；要报告模型间方差、pairwise separability、排名稳定性、错误类型分布。 |
| 可以使用更小模型完成更长轨迹评估 | 设计小模型 Judge 与强模型 Judge 对照，验证小模型在阶段化输入下的可用边界。 |
| 补充动态实时指导实验 | 增加 no guidance、warning-only、steering 三组实验，观察运行期反馈是否提升 Agent 表现。 |

## 3. 研究问题与假设

### 3.1 研究问题

RQ1：DynSTEER 的阶段式评估是否比终态验收、整轨迹一次性 Judge 更可靠？

RQ2：DynSTEER 是否能更清晰地区分不同 Agent 模型和不同 scaffold 的能力差异？

RQ3：在长轨迹任务上，动态分层评估是否能显著降低 Judge 成本，同时保持排序和诊断可靠性？

RQ4：运行期动态指导是否能提升 Agent 任务成功率，或减少错误工具调用、无效轮次、minefield 命中？

RQ5：小模型 Judge 在阶段化输入下是否能替代大模型完成部分长轨迹评估？

### 3.2 可检验假设

H1：相较整轨迹一次性 Judge，DynSTEER 与人工阶段标注或 benchmark 原生 milestone / minefield 结果的一致性更高。

H2：DynSTEER 的阶段分数、minefield 诊断和维度分数能产生更高的模型间可分性，而不只是复刻最终成功率。

H3：动态分层策略在保持排名相关性的前提下，能减少 LLM Judge token、调用次数和 wall-clock 成本。

H4：运行期指导能提升低中等能力 Agent 的成功率，并降低不可恢复错误发生率；对强模型的收益较小但成本浪费减少。

H5：小模型 Judge 在短阶段输入上与强模型 Judge 的一致性高于在整条长轨迹输入上的一致性。

## 4. 实验对象

### 4.1 Benchmark

主实验优先使用当前项目已经接入的 ToolSandbox。

| 层级 | Benchmark | 用途 |
| --- | --- | --- |
| 主实验 | ToolSandbox | 已有 milestone / minefield 标注，适合验证阶段式动态评估、minefield 风险、工具状态一致性。 |
| 扩展实验 | τ-bench 或 BFCL | 若后续完成 adapter，可验证跨 benchmark 泛化。 |
| 压力实验 | ToolSandbox 长轨迹分桶或合成长轨迹 | 验证小模型 Judge 和动态分层策略对长轨迹评估的优势。 |

主实验建议不要一开始全量跑完全部 case，而是分三阶段推进：

| 阶段 | 样本规模 | 目标 |
| --- | --- | --- |
| Pilot | 80-120 cases | 快速验证指标、日志、分析脚本和人工标注流程。 |
| Main | 300-500 cases | 支撑主表格、显著性检验和模型区分度分析。 |
| Full | 全量可运行 cases | 用于最终论文主结果或附录结果。 |

抽样方式应按场景类别、轨迹长度、工具数量、是否包含 minefield、任务难度进行分层抽样，避免只抽到容易任务。

### 4.2 Agent 模型分组

执行模型不在方案中绑定具体商业模型名，正式实验前需要冻结一次模型清单和版本。建议按能力层级分组：

| 组别 | 目的 |
| --- | --- |
| SOTA Agent | 作为当前强基线，验证上界表现。 |
| Strong Agent | 验证与 SOTA 接近时 DynSTEER 能否拉开过程差异。 |
| Mid Agent | 观察运行期指导和动态评估收益是否明显。 |
| Small Agent | 压力测试低能力模型下的错误定位与指导收益。 |
| 同模型不同 scaffold | 验证评估能否区分模型能力与执行框架差异。 |

每个模型至少重复运行 3 次；若成本允许，关键结果用 5 次重复运行计算稳定性。

### 4.3 Judge 模型分组

| Judge 组别 | 说明 |
| --- | --- |
| CheapJudge | 项目内本地结构化评估器，不访问网络，作为低成本基础层。 |
| StandardJudge | 单轮 LLM Judge，用于常规阶段评估。 |
| ExpensiveJudge | 多轮聚焦评估和裁决，用于高风险、高不确定阶段。 |
| SOTA Terminal Judge | 对整条轨迹或终态做一次性评分，作为对照。 |
| Small Stage Judge | 用更小模型评估阶段片段，验证长轨迹低成本可行性。 |

所有 LLM Judge 输入中应隐藏被评估模型名称，避免品牌或模型 ID 造成偏置。

## 5. 实验方法对照组

### 5.1 评估方法对照

| 方法编号 | 方法 | 说明 |
| --- | --- | --- |
| M0 | Benchmark 原生终态验收 | 使用 ToolSandbox 原生结果或最终数据库状态作为基础对照。 |
| M1 | SOTA Terminal Judge | 将完整轨迹和最终状态交给强 Judge 一次性评分。 |
| M2 | SOTA Full-Trajectory Judge | 让强 Judge 对完整轨迹进行过程评分和错误定位。 |
| M3 | Static Stage Judge | 使用阶段切分，但每阶段固定同一 Judge，不启用动态策略。 |
| M4 | DynSTEER Dynamic | 当前 DynSTEER：cheap / standard / expensive 动态调度、动态权重、minefield 和不确定性策略。 |
| M5 | DynSTEER Dynamic + Guidance | 在 M4 基础上，把阶段评估结果转成运行期指导反馈给 Agent。 |

### 5.2 消融设置

| 消融编号 | 设置 | 目的 |
| --- | --- | --- |
| A0 | cheap-only | 检验纯本地评估的上限和误判类型。 |
| A1 | standard-only | 检验固定中成本 Judge 是否足够。 |
| A2 | expensive-only | 检验高成本 Judge 的性能上限和成本不可承受点。 |
| A3 | no dynamic weights | 移除动态权重更新，观察维度自适应的贡献。 |
| A4 | no uncertainty routing | 移除不确定性驱动的评估粒度升级，观察动态调度贡献。 |
| A5 | no minefield policy | 移除 minefield fatal stop，观察安全和风险诊断贡献。 |
| A6 | no stage goal | 不使用预生成 stage goal，仅使用 milestone 原始描述，验证阶段目标生成的贡献。 |
| A7 | small judge full trajectory | 用小模型直接评估整轨迹，对比 small stage judge。 |

## 6. 指标体系

### 6.1 评估有效性指标

| 指标 | 解释 |
| --- | --- |
| Milestone F1 | 动态评估识别 milestone 完成与否的 F1。 |
| Minefield F1 | 识别 minefield 命中与否的 F1。 |
| Human Agreement | 与人工阶段标注的一致性，可用 accuracy、macro-F1、Cohen's kappa。 |
| Native Agreement | 与 benchmark 原生评分或终态结果的一致性。 |
| First Failure Accuracy | 首个失败阶段或首个关键错误定位是否与人工一致。 |
| Score Correlation | 与人工综合分或原生成功率的 Spearman / Kendall / Pearson 相关。 |
| Calibration | 使用 Brier score 或 ECE 评估 judge_confidence / uncertainty 是否可信。 |

### 6.2 区分度指标

| 指标 | 解释 |
| --- | --- |
| Inter-model Variance | 不同 Agent 模型得分方差，越高说明分得更开。 |
| Pairwise Separability | 两两模型得分差的显著性和 effect size。 |
| Ranking Stability | 不同随机种子、不同样本子集下模型排名是否稳定。 |
| Error Profile Distance | 不同模型在错误类型分布上的 Jensen-Shannon distance 或简单分布差异。 |
| Near-tie Resolution | 对终态成功率接近的模型，过程分数是否能给出稳定区分。 |

### 6.3 效率指标

| 指标 | 解释 |
| --- | --- |
| Judge Token | LLM Judge prompt、completion、total token。 |
| Judge Calls | 每个 case 的 LLM Judge 调用次数。 |
| Wall-clock | 单 case 和全 run 的耗时。 |
| Cost per Case | 按供应商价格估算的单 case Judge 成本。 |
| Cost per Rank Fidelity | 达到相同排名相关性所需成本。 |
| Long-Trajectory Capacity | 在固定预算下可评估的最大轨迹长度或 case 数。 |

### 6.4 动态指导指标

| 指标 | 解释 |
| --- | --- |
| Success Rate Delta | 带指导相对无指导的任务成功率变化。 |
| Stage Recovery Rate | 触发 warning 后，后续阶段是否恢复到 pass。 |
| Minefield Avoidance | 指导后 minefield 命中率是否下降。 |
| Tool Error Reduction | 工具调用失败、错误参数、无效查询是否减少。 |
| Extra User Burden | 是否增加不必要澄清或用户轮次。 |
| Premature Stop Rate | 动态策略是否错误提前终止可完成任务。 |

## 7. 主实验设计

### 7.1 实验一：评估可靠性

目标：验证 DynSTEER 的阶段式评估是否比终态验收和整轨迹一次性 Judge 更可靠。

设置：

1. 从 ToolSandbox 分层抽样 120 个 pilot case，主实验扩展到 300-500 个 case。
2. 每个 case 收集 Agent 轨迹、状态快照、原生 milestone / minefield 结果、DynSTEER 阶段报告。
3. 对其中 20%-30% case 做人工盲标，标注阶段完成、minefield、首个失败点和综合过程质量。
4. 比较 M0-M4 在人工标注和原生结果上的一致性。

| Table 1 | 各评估方法与人工标注的一致性。 |

预期结论：

DynSTEER 不一定在所有终态成功率相关指标上压倒 SOTA Judge，但应在阶段完成、首个失败定位、minefield 风险识别和可解释证据上更强。

### 7.2 实验二：模型区分度

目标：验证 DynSTEER 是否能拉开模型和 scaffold 差异。

设置：

1. 使用 4 类能力层级 Agent 模型，每类选 1-2 个代表。
2. 对同一 case 集合运行所有 Agent，固定环境、工具、prompt 模板和温度设置。
3. 每个模型重复运行至少 3 次。
4. 比较原生成功率、终态 Judge 分数、DynSTEER overall_score、阶段维度分数和错误类型分布。

报告：

| 表格/图 | 内容 |
| --- | --- |
| Table 3 | 模型在不同评估方法下的均值、置信区间和排名。 |
| Figure 2 | 模型得分分布箱线图或 violin plot。 |
| Figure 3 | 各模型在 7 个维度上的 radar / bar 图。 |
| Table 4 | pairwise effect size 与显著性检验结果。 |

关键分析：

1. 如果两个模型原生成功率接近，DynSTEER 是否能通过工具质量、恢复能力、安全性或交互质量拉开差异。
2. 如果某模型终态成功但步骤冗余，DynSTEER 的 efficiency 和 tool_quality 是否能体现。
3. 如果某模型中途犯错但最终恢复，recovery 维度是否给出合理奖励。

### 7.3 实验三：低成本与长轨迹评估

目标：验证小模型和动态分层策略在长轨迹评估中的成本优势。

设置：

1. 按轨迹 step 数分桶：短轨迹、中轨迹、长轨迹、超长轨迹。
2. 比较 M1、M2、M3、M4、A7 的成本和一致性。
3. 对每个长度分桶报告 token、调用次数、耗时和与强 Judge / 人工标注的一致性。
4. 重点比较 small stage judge 与 small full-trajectory judge。

| Table 5 | 不同轨迹长度下各方法成本和一致性。 |

预期结论：

阶段化输入能降低小模型 Judge 的上下文压力；DynSTEER 通过 cheap 层和不确定性调度，把强 Judge 调用集中在少数高风险阶段。

### 7.4 实验四：动态实时指导

目标：验证动态评估不仅能“评”，还能在运行期帮助 Agent 少犯错或更早恢复。

分组：

| 组别 | 说明 |
| --- | --- |
| G0 No Guidance | Agent 正常执行，DynSTEER 只旁路评估，不反馈。 |
| G1 Warning Only | DynSTEER 发现低分或高风险阶段时，只记录 warning，不改变 agent 行为。 |
| G2 Soft Guidance | DynSTEER 把阶段诊断压缩成简短反馈，作为下一轮系统或环境提示输入给 Agent。 |
| G3 Stop / Retry | DynSTEER 触发 fatal 或低分阈值时，终止当前路径并允许一次带反馈重试。 |

指导内容格式建议：

```text
当前阶段评估提示：
- 已完成：{matched_milestone}
- 风险：{top_risks}
- 下一步建议：请优先修复 {weak_dimension}，避免 {minefield_hint}
```

约束：

1. 指导内容不能泄露 benchmark 标准答案。
2. 指导内容只能来自已观察到的轨迹证据、阶段目标和结构化约束。
3. 不应把完整 milestone graph 暴露给 Agent。
4. soft guidance 每阶段最多注入一次，避免把评估器变成 planner。

报告：

| 表格/图 | 内容 |
| --- | --- |
| Table 6 | G0-G3 的成功率、成本、minefield 命中率、工具错误数。 |
| Figure 6 | 不同能力层级 Agent 的指导收益。 |
| Case Study 3 | 低中等模型被指导后成功恢复的案例。 |
| Case Study 4 | 指导误导或提前终止的失败案例。 |

预期结论：

动态指导的主要收益应出现在中低能力 Agent 和长轨迹任务中。对 SOTA Agent，指导可能主要减少冗余和风险，而不一定显著提高成功率。

### 7.5 实验五：策略消融

目标：确认 DynSTEER 的关键机制各自贡献。

设置：

1. 固定同一批 case 和 Agent 输出轨迹，离线回放不同评估策略。
2. 比较 A0-A7 与 M4 的可靠性、成本、区分度和误判类型。
3. 对 no dynamic weights、no uncertainty routing、no minefield policy 做单独误差分析。

## 8. 实验流程

### 8.1 准备阶段

1. 冻结代码版本、benchmark 版本、模型版本、prompt 模板版本。
2. 在 `data/toolsandbox/benchmark.json` 中固定 ToolSandbox source root、language、max_workers。
3. 在 `data/toolsandbox/run_config.json` 中按 pilot / main / full 划分 case 集合。
4. 明确每个 Agent 模型的 provider、model、temperature、seed、max token。
5. 明确 Judge 模型的 provider、model、temperature 和输出 JSON schema。

### 8.2 执行阶段

主实验运行：

```powershell
uv run python main.py --benchmark toolsandbox --data-root data --runs-dir runs --results-dir results
```

Docker 环境运行：

```powershell
./scripts/start.sh --benchmark toolsandbox --source ../ToolSandbox --workers 1
```

运行后需要保留：

| 路径 | 用途 |
| --- | --- |
| `runs/<benchmark>/<run_id>/<case_id>/raw/` | 原生 benchmark 运行产物。 |
| `runs/<benchmark>/<run_id>/<case_id>/trajectory.json` | 完整轨迹。 |
| `runs/<benchmark>/<run_id>/<case_id>/raw_summary.json` | 原生摘要和 DynSTEER 运行期诊断。 |
| `results/<benchmark>/<run_id>/<case_id>/report.json` | 单 case 完整评估报告。 |
| `results/<benchmark>/<run_id>/summary.json` | run 级汇总结果。 |

### 8.3 分析阶段

建议新增轻量分析脚本，但不改变核心评估链路：

```text
scripts/analysis/
- aggregate_runs.py       # 汇总多 run、多模型、多策略结果
- compare_evaluators.py   # 计算一致性、相关性、校准和误判类型
- compare_models.py       # 计算区分度、排名稳定性、显著性
- compare_guidance.py     # 分析 no guidance / guidance 对照结果
```

分析脚本输出：

```text
results/analysis/
- evaluator_agreement.csv
- model_separability.csv
- cost_quality_tradeoff.csv
- guidance_effect.csv
- figures/
```

若后续落地代码，脚本应复用当前 `results`、`runs` JSON 结构，不新增核心接口。

## 9. 统计检验

1. 所有平均分报告 95% bootstrap confidence interval。
2. 模型两两比较使用 paired bootstrap 或 Wilcoxon signed-rank test。
3. 多重比较使用 Holm-Bonferroni 校正。
4. 排名一致性使用 Spearman rho 和 Kendall tau。
5. 二分类识别使用 macro-F1、precision、recall、AUC。
6. 成本对比同时报告绝对成本和相对节省比例。
7. 指导实验必须按 case 配对比较，避免不同 case 难度造成混淆。

## 10. 人工标注方案

人工标注不是全量标注，而是作为可靠性锚点。

### 10.1 抽样

从 pilot 和 main 集合中抽取 20%-30% case，覆盖：

1. 成功、失败、warn、missing。
2. 有 minefield 与无 minefield。
3. 短、中、长轨迹。
4. 不同工具类别。
5. DynSTEER 与 SOTA Judge 分歧较大的样本。

### 10.2 标注项

| 标注项 | 取值 |
| --- | --- |
| milestone 是否完成 | yes / no / partial / unclear |
| minefield 是否命中 | yes / no / unclear |
| 首个关键错误 step | step index 或 none |
| 阶段质量 | 1-5 分 |
| 终态是否满足任务 | yes / no / partial |
| 错误类型 | 状态错误、工具错误、冗余、遗漏、交互错误、安全风险、恢复失败 |

### 10.3 质量控制

1. 每个样本至少 2 人标注。
2. 分歧样本由第 3 人裁决。
3. 标注界面隐藏 Agent 模型名称和评估方法结果。
4. 报告 inter-annotator agreement。

## 12. 成功标准

### 12.1 最低可接受结果

1. DynSTEER 与人工阶段标注的一致性不低于 SOTA Full-Trajectory Judge。
2. DynSTEER 的成本明显低于 expensive-only 或 full-trajectory SOTA Judge。
3. DynSTEER 能给出比终态成功率更丰富的错误类型和首个失败阶段诊断。
4. 至少在中低能力模型上，动态指导相对 no guidance 有正收益或显著降低风险。

### 12.2 理想结果

1. DynSTEER 在 milestone / minefield 检测、首错定位、模型区分度上显著优于终态 Judge。
2. Dynamic 策略在 50% 以下 Judge 成本下保持 90% 以上排名相关性。
3. Small Stage Judge 明显优于 Small Full-Trajectory Judge，说明阶段化输入使小模型可用。
4. Guidance 在长轨迹任务中显著提升成功率，并减少 minefield 命中。

## 13. 风险与应对

| 风险 | 应对 |
| --- | --- |
| SOTA Judge 本身很强，DynSTEER 平均分优势不明显 | 强调阶段诊断、首错定位、minefield、成本和区分度，而不是只比总分。 |
| ToolSandbox 原生标注只覆盖部分过程 | 增加人工阶段标注样本，补充首错定位和错误类型。 |
| 不同模型运行成本太高 | 先 pilot，筛选高信息量 case，再扩展 main。 |
| 动态指导泄露答案 | 指导只使用已观察证据和抽象风险，不暴露标准答案或完整 milestone graph。 |
| 小模型 Judge 误判多 | 限定小模型只处理阶段片段，并由 uncertainty routing 升级高风险阶段。 |
| 运行期随机性影响结论 | 固定版本和配置，重复运行，使用 paired 统计检验。 |

## 14. 实施优先级

## 附录A. 项目中没有把握实现的模块部分

1. **运行期指导注入接口**
   - 当前项目已有运行期评估和策略终止能力，但未确认已有接口可以把阶段诊断安全地注入回 Agent 的下一轮上下文。
   - 没有把握点在于不同 benchmark 的 harness 对对话上下文控制方式不同，ToolSandbox 可行方案不一定能泛化到其他 benchmark。

2. **stop / retry 实验闭环**
   - 当前策略终止可以提前停止低质量路径，但“带反馈重试”涉及重新初始化 session、保留任务上下文、避免污染原始实验条件。
   - 没有把握点在于重试会改变 benchmark 原生交互分布，需要单独定义公平对照。

3. **人工标注规模**
   - 方案建议 20%-30% case 人工标注，但实际标注成本和标注员可用性不确定。
   - 若资源不足，可先标注分歧样本和长轨迹样本，以支持关键论点。

4. **跨 benchmark 泛化**
   - 当前仓库明确支持 ToolSandbox adapter；τ-bench、BFCL、WorkArena 等扩展需要新增 adapter 或转换层。
   - 没有把握点在于不同 benchmark 的状态快照、工具调用结构和原生评分接口差异较大。

5. **SOTA / small model 具体名单**
   - 模型供应商和版本变化较快，实验执行前需要冻结模型清单。
   - 方案中只定义能力层级，不直接绑定具体模型名，避免实验还未执行模型版本就过期。

## 附录B. 推荐先跑的最小闭环

最小闭环不做 guidance，先证明评估器价值：

1. 选 100 个 ToolSandbox case。
2. 选 3 个 Agent 能力层级。
3. 每个 Agent 每个 case 跑 3 次。
4. 对比 M0、M1、M3、M4。
5. 人工标注 30 个 case。
6. 输出 Table 1、Table 3、Table 5 和 5 个案例分析。

这组结果足以判断 DynSTEER 的核心实验叙事是否成立，再决定是否投入 P2 的动态指导闭环。
