# DynSTEER 动态评估策略与不确定性修复代码修改方案

生成日期：2026-07-10

## 1. 方案目标

本方案基于 `docs/plans/report/2026-07-10-DynSTEER动态阶段评估算法与Methodology差异核查报告.md` 与用户补充需求，目标是修复当前动态阶段评估主流程中的三类核心问题：

1. 核查并修复 cheap / standard / expensive 各粒度阶段评估结果中 `uncertainty` 的计算与流转问题。
2. 将动态评估策略从“同阶段 cheap -> standard -> expensive 临时升级”改为“当前阶段结果决定下一阶段基础成本与逐维评估粒度”的跨阶段策略。
3. 让 cheap 层不再把 milestone 匹配分数直接复制成整段阶段评估，而是对当前阶段整条轨迹进行低成本综合评估；milestone 分数只作为阶段综合评分中的 progress 证据之一。

本方案明确不修改 `normalize_weights(...)` 与 `update_weights(...)`。动态权重逻辑保持现状，只与新增的跨阶段评估粒度策略并行更新。

## 2. 当前核查结论

### 2.1 `uncertainty` 并非所有最终报告都固定为 0.0，但存在真实缺陷

当前 `StandardJudge` 与 `ExpensiveJudge` 都调用 `LLMJudge._result_from_payload(...)` 生成 `StageEvaluationResult`，该函数确实把 `uncertainty` 初始化为 `0.0`。但在主流程 `_evaluate_stage(...)` 中，standard / expensive 结果会立刻进入 `_enrich_stage_result(...)`，再由 `dynsteer.evaluate.scoring.enrich_stage_result(...)` 调用 `compute_uncertainty(...)` 覆盖 `result.uncertainty`。

因此主流程中已经结算的 milestone stage 和 finish stage 通常不会在最终 `stage_reports` 中固定为 0.0。真正的问题有四个：

1. 直接调用 `StandardJudge.evaluate_stage(...)` 或 `ExpensiveJudge.evaluate_stage(...)` 时，返回结果仍是 `uncertainty=0.0`，该返回值语义不完整。
2. LLM judge 结果的 `required_fields_missing_ratio` 默认保持 0.0，`compute_uncertainty(...)` 对 LLM 证据缺失只能间接依赖 `1 - judge_confidence`，不如 cheap 层完整。
3. `enrich_stage_result(...)` 当前固定 `top2_score=0.0`、`evidence_conflict=False`，不确定性中的 margin 与冲突项尚未真实接入。
4. `pending_required_stage_results(...)` 生成的 synthetic pending stage 不经过 `_enrich_stage_result(...)`，当前会以 `uncertainty=0.0` 出现在最终报告中；这类阶段应视为高不确定或确定失败，而不是零不确定。

### 2.2 当前动态评估策略方向与目标不一致

当前 `_evaluate_stage(...)` 每个阶段都从 cheap 开始，并通过 `select_evaluation_level(...)` 在同一个阶段内升级到 standard / expensive。这与目标策略不一致。

目标策略应为：

- 当前阶段用运行期状态中保存的评估策略决定本阶段评估粒度。
- 当前阶段评估完成后，根据阶段综合分数与逐维分数更新下一阶段评估策略。
- 综合高分：下一阶段基础成本为 cheap。
- 综合合理区间：下一阶段基础成本为 standard。
- 综合低分：不升级到 expensive，而是报警，分析失败原因，并复用当前策略终止机制停止评估和 agent 执行。
- 对低分维度做逐维加严：cheap -> standard / expensive，standard -> expensive。

### 2.3 cheap 层当前不是阶段轨迹综合评估

当前 `CheapJudge` 的核心逻辑是读取 `StageInterval.milestone_score.score`，再把该分数扩散到所有维度。它没有检查当前阶段区间内的工具调用失败、空结果、冗余交互、错误恢复、状态修改风险等轨迹行为。

这会导致 cheap 层实际代表的是 milestone matching，而不是当前阶段整条轨迹的低成本评估。后续修改需要让 cheap 层消费 `stage_trajectory_steps(interval, trajectory)` 的整段阶段轨迹，并把 milestone 分数仅用于 progress 维度和综合分数。

## 3. 推荐方案

推荐采用“结构化策略模块 + 阶段轨迹 cheap 评估 + 运行期 minefield 扫描”的方案。

备选方案对比如下：

| 方案 | 内容 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| 方案 A：最小补丁 | 只改 `_evaluate_stage(...)`，删除同阶段升级，并在 evaluator 内写策略判断 | 改动少 | evaluator 继续膨胀，策略不可独立测试 | 不推荐 |
| 方案 B：策略模块化 | 新增 `dynsteer/evaluate/policy.py`，保存跨阶段基础粒度与逐维粒度；cheap 改为阶段轨迹评估 | 边界清晰，可测试，符合当前包结构 | 需要新增模型和文档 | 推荐 |
| 方案 C：完整 step evaluator | 同时新增独立 `StepEvaluationResult` 与 LLM step judge | 最接近长期 Methodology | 本轮改动过大，容易和动态策略重构耦合 | 暂缓 |

本轮采用方案 B。单步评估层先不做完整独立模型，只把阶段区间内的 step 质量特征接入 cheap 层与阶段报告 metadata。完整 `StepEvaluationResult` 可作为后续版本补充。

## 4. 代码架构设计

### 4.1 新增评估策略模块

新增文件：`dynsteer/evaluate/policy.py`

职责：

- 保存当前阶段使用的评估策略。
- 根据阶段结果计算下一阶段策略。
- 给出低分阶段的策略终止决策。
- 对逐维低分执行 cheap -> standard / expensive、standard -> expensive 的升级。

建议新增数据结构：

```python
@dataclass(frozen=True)
class EvaluationPolicyState:
    base_level: EvaluationLevel
    dimension_levels: dict[Dimension, EvaluationLevel]
    reason: str = "initial"

    def effective_level(self) -> EvaluationLevel:
        ...

    def to_dict(self) -> JsonObject:
        ...


@dataclass(frozen=True)
class EvaluationPolicyUpdate:
    current_policy: EvaluationPolicyState
    next_policy: EvaluationPolicyState
    should_stop: bool
    termination_code: str | None
    termination_reason: str | None
```

策略规则：

```text
低分阶段：
  result.status in {fail, missing, invalid}
  或 result.stage_score < thresholds.warn_threshold
  -> should_stop=True，不升级到 expensive

高分阶段：
  result.stage_score >= thresholds.pass_threshold + thresholds.threshold_margin
  且 result.uncertainty <= thresholds.low_uncertainty
  且 fatal_minefield_score == 0
  -> next base_level = cheap

合理阶段：
  其他未终止阶段
  -> next base_level = standard

逐维低分升级：
  dimension_score < thresholds.fail_threshold -> expensive
  thresholds.fail_threshold <= dimension_score < thresholds.warn_threshold:
    base=cheap -> standard
    base=standard -> expensive
  其他维度使用 base_level
```

由于现有 `StandardJudge` 与 `ExpensiveJudge` 都是整阶段全维度评估器，实际执行时不做“只评估某个维度”的局部 judge 调用，而是用 `EvaluationPolicyState.effective_level()` 取基础粒度和逐维粒度中的最高成本作为本阶段实际 judge。逐维策略仍保存在 metadata 中，作为下一步拆分专项 evaluator 的接口。

### 4.2 修改运行期状态

修改文件：`dynsteer/evaluate/runtime.py`

`RuntimeEvaluationState` 增加：

```python
evaluation_policy: EvaluationPolicyState
minefield_matches: list[JsonObject] = field(default_factory=list)
max_minefield_score: float = 0.0
fatal_minefield: bool = False
```

初始化时：

```python
evaluation_policy=initial_evaluation_policy()
```

默认初始策略：

- `base_level=EvaluationLevel.CHEAP`
- 所有维度为 cheap
- 原因记录为 `initial`

### 4.3 重构阶段评估调度

修改文件：`dynsteer/evaluate/evaluator.py`

移除当前 `_evaluate_stage(...)` 中基于 `select_evaluation_level(...)` 的同阶段升级链路。新的流程：

```text
policy = state.evaluation_policy
level = policy.effective_level()

if level == cheap:
    CheapJudge.evaluate_stage(...)
elif level == standard:
    StandardJudge.evaluate_stage(...)
elif level == expensive:
    ExpensiveJudge.evaluate_stage(...)

enrich_stage_result(...)
update_weights(...)
update_evaluation_policy(...)
```

`select_evaluation_level(...)` 不再作为动态策略入口。建议删除该方法，并更新 `docs/apis/evaluate.md` 与 `docs/apis/judges.md` 中“cheap 不足时同阶段升级”的描述。

如果 `policy.effective_level()` 要求 standard 或 expensive，但对应 judge 未配置，继续抛出 `JudgeConfigurationError`。这比静默回退 cheap 更安全。

### 4.4 cheap 层改为阶段整段轨迹综合评估

修改文件：

- `dynsteer/judges/cheap.py`
- `dynsteer/evaluate/quality.py`

新增或扩展阶段区间质量函数：

```python
def build_stage_quality_diagnostics(interval: StageInterval, trajectory: Trajectory) -> JsonObject:
    """构造当前阶段区间内的低成本轨迹质量诊断。"""
```

该函数只分析 `stage_trajectory_steps(interval, trajectory)` 返回的当前阶段步骤，不扫描整条轨迹。

cheap 维度分数建议：

| 维度 | cheap 数据来源 |
| --- | --- |
| progress | `interval.milestone_score.score`；无 milestone 时按 interval status 处理 |
| state_consistency | 状态更新类 step、tool result 与 milestone evidence 的一致性低成本规则 |
| tool_quality | 工具失败、异常、空查询结果、疑似别名参数 |
| efficiency | 阶段 step 数、重复工具调用、首次工具前多轮用户负担 |
| safety | fatal minefield 由 enrich / runtime guardrail 覆盖；cheap 层先按硬失败和错误 step 降分 |
| interaction_quality | agent 面向用户消息是否缺失、错误后是否解释 |
| recovery | 工具失败后是否重试、解释或安全降级 |

`CheapJudge.evaluate_stage(...)` 不再把同一个 milestone 分数复制到所有维度，而是先构造 `dimension_scores`，再按 `weights` 计算 `stage_score`。为避免和 `LLMJudge._stage_score_from_dimensions(...)` 重复实现，建议把加权求分逻辑抽到 `dynsteer/evaluate/scoring.py` 的公共函数：

```python
def stage_score_from_dimensions(
    dimension_scores: dict[Dimension, float],
    weights: dict[Dimension, float],
) -> float:
    ...
```

`LLMJudge._stage_score_from_dimensions(...)` 调用该公共函数，避免 cheap 与 LLM judge 分别维护一套加权逻辑。

### 4.5 修复 uncertainty 语义

修改文件：

- `dynsteer/judges/base.py`
- `dynsteer/judges/cheap.py`
- `dynsteer/evaluate/scoring.py`
- `dynsteer/evaluate/runtime.py`

修改点：

1. `LLMJudge._result_from_payload(...)` 不再返回误导性的 `uncertainty=0.0`，初始化为 `1.0 - validated.judge_confidence`。
2. `CheapJudge.evaluate_stage(...)` 初始化 uncertainty 时根据 missing ratio 和 confidence 给出低成本估计，主流程 enrich 仍可覆盖。
3. `pending_required_stage_results(...)` 中 synthetic pending stage 设置为 `uncertainty=1.0`，并在 diagnosis 中明确“required milestone 未完成，结果高风险”。
4. `enrich_stage_result(...)` 保持作为主流程最终 uncertainty 计算入口，但需要把 `uncertainty_inputs` 写入 `result.metadata`，便于审计：

```python
result.metadata["uncertainty_inputs"] = {
    "top1_score": top1,
    "top2_score": top2,
    "missing_ratio": result.required_fields_missing_ratio,
    "stage_score": result.stage_score,
    "judge_uncertainty": 1.0 - result.judge_confidence,
}
```

5. 本轮不强行补真实 `top2_score`。如果后续要接入 milestone candidate margin，应先把 `analyze_milestone_step(...)` 的候选分数摘要传入 `StageInterval` 或 stage metadata，避免从日志结构反向解析。

### 4.6 运行期 minefield 扫描修复

修改文件：

- 新增 `dynsteer/evaluate/minefield.py`
- 修改 `dynsteer/evaluate/evaluator.py`
- 修改 `dynsteer/evaluate/scoring.py`

新增运行期 boundary 扫描：

```python
def evaluate_minefields_at_boundary(
    graph: MilestoneGraph,
    trajectory: Trajectory,
    boundary: Boundary,
    scorer: GeneralScorer,
    context: ScoringContext,
) -> tuple[list[JsonObject], float, bool]:
    ...
```

source 解析规则与 milestone 保持一致：

- `ConstraintTarget.STATE_SNAPSHOT` 使用 `boundary_snapshot(boundary, trajectory.snapshots)`。
- `ConstraintTarget.TOOL_CALL` / `TOOL_RESULT` / `STEP` 使用 `boundary_step(trajectory, boundary)`。
- `ConstraintTarget.METRIC` 使用 `trajectory.metrics`。

为避免复制 `GeneralScorer._constraint_sources(...)` 私有逻辑，建议将其提升为公共方法：

```python
def constraint_sources(
    self,
    constraint: Constraint,
    boundary: Boundary,
    trajectory: Trajectory,
    snapshots: list[StateSnapshot],
) -> tuple[object, StateSnapshot | None]:
    ...
```

运行期主循环在 `trajectory.append_step(step)` 后、`analyze_milestone_step(...)` 前扫描当前 boundary。命中 fatal minefield 时：

- 写入 `state.minefield_matches`。
- 设置 `state.fatal_minefield=True`。
- 如果 `config.stop_on_minefield` 为 True，立即复用现有 `harness.stop_case(...)` 与 `evaluator_policy_stop` 日志流程。

`evaluate_minefields(...)` 可保留为最终汇总入口，但内部应改为扫描已记录的运行期结果或全历史 boundary，而不是只读 `trajectory.final_state`。

### 4.7 minefield penalty 接入最终评分

修改文件：`dynsteer/evaluate/scoring.py`

当前 `overall_score(stage_reports, minefield_score)` 只使用 max minefield score。建议新增 penalty 聚合函数：

```python
def minefield_penalty_score(matches: list[JsonObject]) -> float:
    ...
```

规则：

- `penalty.mode == "fixed"`：命中分数乘以 `penalty.value`，`fixed=1.0` 可把整体分数归零。
- 未提供 penalty 的历史 match 保持使用 `score`，避免运行期旧数据无法汇总。

`TrajectoryEvaluationReport.minefield_matches` 中增加 `penalty` 字段，方便展示与审计。

## 6. 关键行为约定

### 6.1 低分阶段终止口径

低分阶段不升级 expensive。只要当前阶段综合结果满足以下任一条件，就生成策略终止决策：

- `stage_result.status in {FAIL, MISSING, INVALID}`
- `stage_result.stage_score < thresholds.warn_threshold`
- `stage_result.fatal_minefield_score >= thresholds.fatal_minefield_threshold`

终止原因沿用现有 `RuntimeEvaluationDecision` 与 `evaluator_policy_stop` 日志，不新增第二套停止流程。

### 6.2 standard / expensive 的阶段轨迹语义

`StandardJudge` 与 `ExpensiveJudge` 已通过 judge prompt 消费 `stage_trajectory_steps(interval, trajectory)`，天然是阶段整段轨迹评估。本轮重点是：

- 删除同阶段升级调度。
- 由运行期策略决定是否调用 standard / expensive。
- 强化 prompt 文档，明确 progress 维度必须结合 `interval.milestone_score` 和 `structured_milestone_evidence` 判断。

### 6.3 不修改动态权重函数

以下函数保持不改：

- `dynsteer.evaluate.scoring.normalize_weights(...)`
- `dynsteer.evaluate.scoring.update_weights(...)`

如果实施中需要新增策略配置或策略状态，不复用或改写动态权重配置。

## 8. 实施顺序

推荐顺序：

1. 先修 `uncertainty`，因为它会影响后续策略判定。
2. 再修 cheap 阶段轨迹综合评分，保证策略输入不再只是 milestone 分数。
3. 新增策略模块并用纯单元测试锁定高分 / 合理 / 低分 / 逐维升级行为。
4. 重构 evaluator 调度，删除同阶段升级链路。
5. 修复 minefield boundary 扫描与 penalty。
6. 最后更新 API 文档和展示层。

## 9. 风险与回滚点

| 风险 | 影响 | 控制方式 |
| --- | --- | --- |
| 无 LLM 配置时策略要求 standard / expensive | 运行到下一阶段时报 `JudgeConfigurationError` | 保持显式失败，不静默回退 cheap；文档说明需要配置 LLM |
| cheap 新规则过严导致低分终止变多 | 可能提前停止更多 case | 用测试覆盖典型通过场景，并把 warning 类规则控制在对应维度，不直接全局归零 |
| minefield boundary 扫描产生重复 match | 报告重复、分数重复扣除 | 在 `RuntimeEvaluationState.minefield_matches` 中按 `(minefield_id, boundary_id)` 去重 |
| 删除 `select_evaluation_level(...)` 影响外部调用 | 旧 API 不再可用 | 当前约束不要求兼容旧接口；更新 docs/apis |

## 10. 不纳入本轮的事项

1. 不接入参考轨迹 / reference route。
2. 不修改 milestone DAG + immediate dominator 阶段划分。
3. 不修改 `normalize_weights(...)` 与 `update_weights(...)`。
4. 不实现完整独立 `StepEvaluationResult` 与 LLM step judge；本轮只把阶段内 step 质量特征接入 cheap 综合评分和 metadata。
5. 不新增只包一层已有函数的中转函数。

## 附录A. 项目中没有把握实现的模块部分

1. **完整独立 step-level LLM evaluator**：没有纳入本轮方案。原因是用户补充明确本轮粒度评估应针对当前阶段整条轨迹，而不是把当前修复重心放在每个 step 的独立 LLM 判分；同时完整 step evaluator 会引入新的 prompt、结果模型、FirstErrAcc 指标和成本控制策略，范围明显大于本次动态策略修复。
2. **真实 top2 milestone margin 接入 uncertainty**：当前 `analyze_milestone_step(...)` 的候选分数主要保存在诊断详情中，而 `StageInterval` 没有结构化携带 top2 候选分数。本轮只记录 `top2_score=0.0` 的 uncertainty 输入，不从日志结构反向解析。若要真实接入，需要先扩展阶段 interval 或 matching result 模型。
3. **逐维专项 evaluator**：本轮保存 `dimension -> EvaluationLevel` 策略，但实际调用仍使用最高成本的整阶段 judge。原因是现有 standard / expensive judge 都是全维度阶段评估器，若要只对某些维度单独调用专项 judge，需要新增 prompt 模板、结果合并规则和冲突裁决逻辑。
4. **minefield penalty 的非 fixed 模式**：当前模型只有 `mode` 与 `value`，历史数据中是否存在 fixed 之外的模式尚未确认。本轮可以实现 fixed 与默认比例扣分；其他模式应在发现真实数据后再扩展。
